## 2. 三项 P2

### P2-A：确认取消后不再出现过时的停止失败提示

- **修复：**每条操作失败提示可以带一个“由新快照证明不成立”的条件。停止请求的条件是：服务端已记录停止（`cancelRequested`），或任务已不在运行。
  - 只有满足这个条件的快照才会隐藏提示。
  - 无论失败先到还是快照先到，结果都一样。
  - 其他失败，以及任务仍在运行、未请求停止时的停止失败，都照常显示。
- 作品、任务和操作身份的隔离沿用原有机制，切换后迟到的结果不会写入新状态。没有新增 POST，续跑语义不变。

### P2-B：同一页面作用域内的读取串行

- **修复：**每个页面作用域（一部作品，挂载期间）最多只有一个 GET 在途。
  - 在途期间的补读请求（轮询、操作回执、手动重查）合并成一次，在当前请求结束后再读。
  - 在途请求的结果可能早于发起补读的动作，因此丢弃，不当作最终确认。
  - 如果操作回执直接显示时恰好有慢轮询在途，也会在它之后再读一次，旧结果不会覆盖新状态。
- 任务进入终态后停止自动轮询，手动“重新读取”和显式续跑仍可用。
- 切换作品或卸载页面会开启新作用域。旧请求既不写状态，也不调度新的定时器。

### P2-C：锁测试失败时回收持锁连接

- **修复：**确定性锁用例改用 `holdingProjectLock`。
  - 获取连接、BEGIN、持锁和等待断言都在可靠的收尾里执行：测试主动放行时 COMMIT，未放行就失败时 ROLLBACK，ROLLBACK 也失败时销毁这条连接（关闭它自己的 socket）。
  - 排队中的导入和保存 Promise 都登记过，在有时限的等待内全部结算，不会留下未处理的拒绝。
  - 清理问题不会覆盖测试本身的失败，只记入证据；测试本身通过但清理失败时，判为失败。
- 本文件的连接池会记录会话错误，不会因此中断整个运行。
- `afterAll` 先写证据，再逐个在时限内关闭连接池。
- 只终止本场景自己命名的持锁会话（按应用名、并要求它持有事务锁），不碰其他会话。
- **失败路径回归：**故意失败的三个子场景，都由外层断言精确核对：
  1. 放行前抛错：原错误保留，ROLLBACK，排队的导入随后写入三集，无阻塞会话，持锁连接回到连接池并可用。
  2. 持锁会话在回滚前丢失：原错误保留，连接被销毁，清理问题已记录，排队任务已结算。
  3. 测试本身通过但清理失败：判为失败，错误信息是“lock holder cleanup failed”。

## 3. 浏览器闭环

**组成：**
- Chrome for Testing（无头），驱动 `pnpm build` 构建的 Next 应用（`next start`，127.0.0.1:3010）。
- 页面只通过网页自己的同源 `/api/v1` 代理访问 API。代理在构建时编译为默认上游 127.0.0.1:3001。驱动前先确认了经代理访问 `/api/v1/writing/title-runs/options` 返回 200、`TITLE_WRITING_READY`。
- API 是真实的 Nest 应用（真实控制器、服务、存储、文本链）。
- 数据库是一次性的 PostgreSQL 16.15。

**模型替身的接入方式：**
- 与真实 API 验收相同：只在测试里替换控制器用的标题创作服务，transport 换成计数替身，不打开网络连接。
- 运行时自带的标题创作保持关闭，也没有任何供应商密钥。
- 没有增加生产 Mock 回退，也没有放宽供应商白名单。
- 浏览器端没有使用 `route.fulfill`，没有模拟 fetch，也没有用静态 JSON 代替业务 API。
- 因此这次验收证明的是真实业务逻辑，**不能证明正式 StudioRuntime 的启用配置及其恢复定时器已经验收**。

样例文字来自替身 fixture，每个剧名都以“模型替身样例·”开头，截图上能直接看出来。

### A. 主流程（作品 `4df5e3f5…`，任务 `1e1e2f81…`）

1. 打开 `/create`，填写剧名和“配置与权限”中的操作者令牌，点击“AI 一键创作”。页面只发了两个写请求：创建作品、启动任务。
2. 跳转到 `/projects/{id}/writing`，替身把第 1 集挂起，页面显示“正在编写第 1 集”，此时替身已收到 3 次请求。
3. 运行中刷新：恢复了同一作品、同一任务。约 5 秒内（超过两次轮询间隔）新增调用 0 次，页面新增写请求 0 个，该作品仍只有 1 个任务。
4. 放行后，页面显示“创作完成”，故事、大纲、三集剧本都在。合计调用 5 次，故事版本为 DRAFT 且是作品的当前故事。
5. 页面显示“剧本已经生成并保存在这次创作里。按审核规则，故事通过审核后才能把剧本写入各集草稿……”，没有任何一集标为“已写入”。数据库中剧本版本为 0。
6. 点击“查看和修改故事草稿”，进入现有新手流程的故事步骤，在检查面板依次点“提交审核”、“通过”。两次审核请求都返回 200，数据库中该任务的故事 `d7850b15…` 变为 APPROVED。
7. 回到进度页，**双击**“写入剧本草稿”：页面只发出 1 个 POST。
8. 三集都显示“已写入剧本草稿”。三个剧本版本都是 DRAFT，来源都是 `d7850b15…`，并且都是各集的当前版本，与任务里记录的 `scriptRevisionId` 一致。三个版本 id：`1695b17e…`、`4c9575f1…`、`8f515e34…`。
9. 从“去修改这一集剧本”进入工作台，第 1 集编辑器中的正文与数据库一致。新手流程第 2 步“看剧本”中，三集的正文也都一致。
10. 刷新后仍是 3 个版本，“写入剧本草稿”按钮不再出现，没有重复版本，调用仍是 5 次。

### B. 冲突流程（另一部作品 `d87f0f5a…`）

- **通过页面完成：**启动、审核故事（提交审核、通过）、写入剧本草稿。
- **通过 API 准备：**在审核通过后、写入之前，直接调用 API 为第 2 集写入一份人工剧本 `90841120…`。这一步只是准备数据，不是用户操作。
- **结果：**
  - 页面按集显示：第 1 集“已写入剧本草稿”，第 2 集“该集已有剧本，没有覆盖”，第 3 集“已写入剧本草稿”。
  - 页面上没有“全部写入”或“全部完成”字样。
  - 第 2 集只有那份人工版本，正文没变，仍是当前版本。整部作品共 3 个剧本版本。

### C. 结果未知与身份恢复（作品 `41d2e1ce…`）

- 替身让第一次故事策划请求返回 503，形成“已发送、结果不确定”的调用。页面显示“需要处理”和“结果不确定”。
- 刷新以及约 5 秒的普通读取之后，调用仍是 1 次，没有自动重发。
- 续跑按钮在两种情况下都不可用：只填令牌、没勾选“我知道……可能已经产生费用”时；勾选和令牌都缺时。两项都满足后才可用。
- **网络注入（只有这一处）：**
  - 第一次续跑请求原样转给服务端（`route.fetch`）。确认服务端返回 200 且数据库已有 1 条续跑记录后，才在返回浏览器的途中中断（`connectionreset`）。
  - 页面显示“没有确认续跑是否已被受理（网络或服务异常）。再次点击会重放同一个续跑请求。”
- 再次点击后，页面用**同一个幂等键**重放，任务完成。续跑记录仍是 1 条。
- **调用记录：**`concept#1 unknown`、`concept#2 completed`、outline、episode 1–3 各 1 次，合计 6 次。重放没有增加调用。
- **令牌与密钥：**页面的 localStorage、sessionStorage 和 cookie 里都没有操作者令牌或替身密钥。
