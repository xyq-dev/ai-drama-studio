# ViMax E2-B：持久候选与单场景审核保存

状态：代码、本地分项与独立隔离验收已完成。**SQL 仍为草案，业务库未执行、线上未启用。** 本阶段不运行 ViMax、模型或媒体供应商，不交付完整 E2 的发送治理与 E3 真实规划。代码集成和最终提交 CI 的实时结果以 [接续记录](VIMAX_E2B_PROGRESS.md) 所指功能分支 PR 为准。

## 用户流程

1. 在短剧工作台的剧本页完成 [单场景预览](VIMAX_PLATFORM_PREVIEW.md)，选择与原文场次/标题匹配、已有且没有活动镜头的场景，点「保存候选」。候选保存在服务器，刷新或重新进入后可从候选列表找回，无需重新导入文件。
2. 打开候选，对照冻结原文、逐句对白与分镜，确认后「保存场景草稿」。系统为同一个 scene ID 创建新修订，保留原序号、地点引用和历史版本；不取代整集。
3. 点「打开场景审核」，通过现有审核页人工提交/批准候选实际创建的精确场景修订。候选保存本身不表示批准。
4. 场景为当前、已批准且 CURRENT 的那个精确修订时，再确认并点「写入镜头草稿」。镜头、预计时长、角色引用及永久映射一次性提交；镜头仍需原有人工审核。

目标发生人工修改、新增镜头、剧本/角色变版、来源过期、依赖传播尚未完成或同集整集拆解进行中时阻断新写入，保留可读候选。其他场景/镜头及其来源边不被改写；依赖目标旧修订的资产继续使用已有 STALE 规则，独立邻场资产不受影响。首版不开放已有镜头的取代、任意场景重排、接受人工变版继续写入或自动批准。

E2-A 预览响应仍然 `writeAllowed:false`、`persisted:false`，不能当作写入凭证。E2-B 使用独立版本化候选与命令，服务端在实际写入事务中重新判断资格。整个阶段模型调用和新增费用记录为零。

## 契约与接口

契约位于 `packages/contracts/src/vimax-candidate.ts`；全部路径以 `/api/v1/projects/:projectId/episodes/:episodeId/vimax-candidates` 为前缀，沿用站点登录、CSRF、工作区/操作者隔离和私有不缓存响应。production 环境关闭；系列文本作品拒绝此入口。

| 方法 | 相对路径 | 行为 |
| --- | --- | --- |
| GET | `/targets` | 当前来源及最多 100 个目标场景、行版本和阻断原因；只读 |
| GET | 空路径 | 持久候选分页，默认 10、最大 20，作用域绑定的不透明游标 |
| GET | `/:candidateId` | 冻结方案、永久回执、当前场景及实时写入资格；历史可读不代表当前可写 |
| POST | 空路径 | `ads.vimax-candidate.create.v1`：已有平台请求加目标 scene ID/修订/行版本；只保存经服务器重新核验的完整候选 |
| POST | `/:candidateId/scene` | `ads.vimax-candidate.save-scene.v1`：expectedVersion 与显式人工核对确认；保存场景草稿 |
| POST | `/:candidateId/shots` | `ads.vimax-candidate.place-shots.v1`：expectedVersion 与显式人工核对确认；写入精确已批准场景的镜头草稿 |

三种 POST 均需要 `Idempotency-Key`；操作者与工作区由服务器确定，trace ID 进入真实审计事件。所有输入严格校验，不接受上传报告或客户端批准状态。HTTP 请求仍为 300 KiB 上限；冻结记录另按 compact JSON 1 MiB 限额，SQL 的 JSONB 文本上限为 1.5 MiB，给数据库序列化空格留余量。超限返回明确 413。持久化另外拒绝 PostgreSQL JSONB 不支持的未配对 Unicode surrogate；有效 emoji 与原文空格/换行不被归一化。

新请求、冻结快照和阶段命令各有版本化哈希。目标/命令版本是有意义的身份字段，必须计入哈希，不能套用旧文本哈希对 volatile 字段的排除规则。对白按原文逐字写入，不使用会 trim 对白的旧格式化器；首尾帧、机位树等扩展字段保留在严格候选结构，不藏入 camera 或 promptText。

## 永久状态与重放

状态仅向前：`stored`（候选版本 1）→ `scene_saved`（2）→ `shots_saved`（3）。场景人工审核会正常递增 scene 行版本，所以镜头阶段校验精确 revision 和当前批准指针，不比较候选最初的 scene 行版本。

创建使用 `(workspace, actor, idempotency_key)` 永久唯一键；两个保存阶段各永久记录其原 key、请求哈希、精确资源 ID 和结果。已成功的原键同内容重放先返回原结果，不受此后来源、审核或活动任务变化影响，也不新增修订、事件、镜头或费用。同键不同内容返回 409；已保存阶段使用不同键不会再执行。

浏览器在发送前把原 key、严格请求体、操作和候选 ID 暂存于当前标签页 sessionStorage，不保存令牌或模型密钥。无法保存请求身份时不发送。断连、5xx、鉴权变化或不完整成功回执保留原身份，刷新后只能显式确认原请求，不能用新来源改写旧请求或自动换键。确认原回执不依赖后来变化的 UI 写入资格。完整且关联匹配的回执才能清除自己的请求身份，迟到回应不能删除较新的身份。候选内容的持久来源是服务器，不依赖浏览器临时副本。

## 数据库与并发边界

新增两表：`vimax_storyboard_candidate` 保存严格冻结快照、来源/目标、哈希、前向状态及永久回执；`vimax_storyboard_candidate_shot` 保存每镜实际 shot/revision 到候选保存场景的永久映射。复合外键限制 workspace/project/episode/scene，唯一键与触发器保护不可变输入、回执、精确新场景修订归属和连续完整镜头映射。

写事务锁序为：工作区 `title_writing_run` advisory 锁 → 候选 → project → episode → scene → shots。同集 running 的整集拆解只查询、不再反向锁运行行。原回执判断优先；新操作在项目锁内使用同一个连接重读完整来源，保留 pending STALE 阻断，并复核目标版本和零活动镜头。任一步失败，修订、角色引用、映射、事件和候选状态全部回滚。

GET 使用一致的只读快照，源变化不导致历史方案消失。读失败不被当作空列表；过期或加载失败的 UI 资格不能继续授权新写入。所有真正的写入决定仍由服务器事务完成。

## SQL 草案与启用

文件：`packages/database/prisma/drafts/20261031000100_vimax_storyboard_candidate.sql`。仅创建两张新表、索引和守卫；前置为既有七个 base migrations 和 `20261012000100_script_breakdown`，不要求系列迁移。它不在通用 migration 发现目录，不在应用启动、读取或维护时自动执行，也不登记为已经应用的正式迁移。

结构缺失、版本标记/守卫或必要列不完整时，新 API 明确 503，E2-A 预览继续可用。查询/权限/连接故障不伪装为“缺表”。**业务库执行与测试站点部署仍需各自可用连接和执行权限；代码合并或隔离验证通过均不代表业务库已启用。**

独立 CI 工作流为 `vimax-candidate-acceptance.yml`：runner-local PostgreSQL 服务，两个不同、全新的空库分别执行存储和真实 HTTP 验收；没有生产数据库 URL、模型 key 或部署 secret。执行前需要三项 `TITLE_WRITING_ACCEPTANCE_*` 变量，以及额外的 `VIMAX_CANDIDATE_ACCEPTANCE_DRAFT_AUTHORIZED=true`；连接后还只读确认真实库名和全库无表，再执行既有迁移和经审查草案。普通 test、integration 与 migrate 不执行此草案。

代码回滚不回退数据库、不删除永久回执。旧代码可继续读取已有合法 Scene/Shot 历史；两个候选表保留，后续采用前滚修复。业务启用前应核对最终审查提交的草案文件及前置迁移，单独记录实际执行和版本；本页不提供自动业务迁移入口。
