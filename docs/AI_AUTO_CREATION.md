# AI 自动创作（2026-10-18）

用户只填一句想法、只选题材，或什么都不填，确认规模和调用预算后点一次「AI 自动创作」。服务端自动完成：

资料整理 → 研究与受众分析 → 原创选题比较与规则选择 → 故事与结局、人物关系、地点道具 → 分集大纲 → 逐集剧本 → 程序检查 + 独立 AI 审阅 → 最多两轮定向修改 → 保存为「AI 自动生成草稿」并导出成品剧本包。

本功能交付的是**自动生成的剧本包与生产准备包**：故事以「AI 自动生成草稿」保存，分集剧本要写入作品，仍须先由人在作品中审核通过故事（机器质量检查不代替人工审核，本功能不会自动写 APPROVED）；不生成图片、语音或视频。「剧本包完成」与「视频成片完成」是两个状态，后者在本功能里永远是「未开始」。

## 3. 研究层：只说真正读到的

- 三个官方入口（巨量引擎帮助中心 1 条、巨量学堂课程 2 条）2026-10-18 实际请求得到的是**前端脚本渲染的空壳**，没有标题或正文。内置快照如实记为 `unreadable / readScope=none / excerpt 空`，不能被引用。
- 项目知识库条目 `S-KB-CRAFT`：本仓库从 drama-skills（MIT，commit c2426e0）改编的写作方法原文，只涉及结构与节奏，**不含任何受众或市场数据**。
- 公开页面读取：`AUTO_CREATION_RESEARCH_FETCH=true` 才开启，只读白名单主机（默认两个官方主机）。仅 https/443、拒绝 IP 字面量和带账号的地址、DNS 结果命中回环/私网/链路本地/共享地址/元数据/组播即拒绝（IPv6 先解码成 8 组，任何写法的 IPv4 映射、兼容、NAT64、6to4 地址都按其中的 IPv4 判断）、连接钉在已检查的 IP（防 DNS 重绑定；按 Node 24 的 lookup 约定同时回应单地址与 `all: true` 地址数组两种调用，不复用连接池中的连接）、证书仍按主机名校验、不跟随重定向、512 KB 上限，以及覆盖 DNS 解析和请求、与是否持续收到数据无关的每个网址 8 秒绝对截止（截止或超限时一律按失败处理，不会把读到一半的正文当成完整页面）。真实的 `node:https` 读取路径由本地 TLS 测试服务器覆盖（测试专用 CA，`packages/providers/src/test-fixtures/research-tls`）。外部文字放在标明「不可信」的数据块里，提示词要求忽略其中任何指令。
- 没有视频画面或音频理解能力：所有参考内容只按文字分析，页面和剧本包都写明「没有观看任何视频」。
- **程序校验（拒收而不是提醒）**：引用必须是快照中**已读取**的条目；事实的 `evidence` 必须**完整地出现在某一条**所引资料原文中（把两条资料首尾拼起来得到的句子不算引文）；任何数字（含「百分之六十」「18 岁」「3 万」「两成」，以及「十名」「八名」「三百人」「五十元」「三次」等中文人数、次数、金额）必须作为**完整数字**出现在所引资料原文里（原文只有「2018年」不能支持「18岁」，「一百八十人」不能支持「八十人」）；序数（第三集）、单独的「一个/一次」以及「一致、一定、一旦」等普通词不算数字。本次任务自己的集数、每集秒数和分钟数只在描述本任务计划的分句里可以不引用来源，凡是出现用户、观众、平均、每天等统计用语的分句（如「用户平均每天观看60秒」「观众每天观看1分钟」）即使数值恰好相同也需要来源；没有来源的假设（含验证方式）、受众、机会、局限和**采用的约束**中不能出现数字。
- 受众标为「有来源」时，受众**自己引用的**资料中必须至少有一条合格的市场资料（官方入口、已读取、带发布日期、一年内）；只引用写作方法、参考页面、用户资料或无日期/过期页面一律拒收（`unsourced_claim`），不看全局模式。资料有限模式下受众一律不能标为「有来源」。
- 只有**官方入口**读到的、带发布日期、一年内的资料才算市场资料；用户提供的参考网址一律按参考资料处理，不会让任务变成「有来源」。只有可读、带发布日期、一年内的市场资料才算「有来源」；否则进入**资料有限策划模式**，开始页、运行页和剧本包都明示「不是实时市场验证」。以当前内置快照，默认就是这个模式。

### 3.1 研究的数字契约与拒收诊断（2026-10-19，prompt.v2 / checks.v2）

测试站一次真实任务（1 集、60 秒、0 轮修改、预算 6、空想法、资料有限模式、DeepSeek）在研究阶段被 `unsourced_number` 拒收，只发送 1 次；当时只存了规则名，模型回答按设计没有保存，所以**触发拒收的原文和字段没有确认**。核对代码后确认的是提示词与检查之间的矛盾，而不是某一句具体文本：

- 旧提示说「数字只能原样引用资料区里出现过的内容」，又要求在局限里写「时效」，而无法读取的官方条目的说明里带着 2026-10-18 这样的日期；但检查只认所引资料**摘录正文**里的数字，假设、验证方式、机会和局限里一律不许有数字。按旧提示写出日期、资料条数、「上线后统计 7 天」「前 3 秒」这类内容都会被整份拒收（见 `packages/domain/src/auto-creation.spec.ts` 中标明为**合成样本**的复现）。
- 「采用的约束」（`appliedConstraints`）此前完全不检查：统计数字放进这个字段就能绕过检查。
- 「第 3 集」这样带空格的序数被当成数字（多集任务里会误拒）。

v2 的处理：

- 提示词明确列出哪些字段的数字必须出自所引资料的摘录正文、哪些字段不写任何数字（含日期、条数、百分比、年龄、人数、天数、秒数、次数），并给出资料有限模式的合法写法：facts/observations 可以为空，受众只能是假设，不得为填满字段编造市场事实。无法读取的条目在提示里只列编号、标题和状态，不再附带含日期的说明。
- 检查：采用的约束与其他无来源字段同样检查；选题方向的 `audienceFit` 也不得有无来源数字（一句话故事等故事内容里的数字不受限）；只有表示作品或计划内结构位置的序数不算数字：后面紧跟集、场、幕、章、节、轮、秒、次、个等单位（「第 3 集」「第二场」「第一次」，带不带空格都一样），或在分句开头作条目编号（「第一，…」）；其余的「第 N」都是名次（如「播放量第 3」「销量第 3」「口碑第一」「第三名」），按名次数字处理，必须有来源，资料原文里的同一名次（带不带空格）可以支持；出现在排名语境（排名、排行、榜、名列、位列、位居、热度、人气、冠军）里的序数（如「排名第一」「位列第 3」「热度第一」）一律按名次处理（旧检查完全不认这类排名）。本任务冻结的集数、每集时长，以及**设置了的**人物、地点上限可以照写，但人物、地点上限只在数字紧挨着「人物/角色」「地点/场景」及「最多、不超过、上限」等限定词时才算（如「出场人物最多 4 人」「三处地点」），且数值必须等于冻结值；凡含观众、用户、平均、占比等统计用语，或排名、榜、热度、人气、爆款、热门、播放、「前 N」等排名与市场用语的分句，一律不豁免。其余既有保护（中文数字、完整数字边界、近期市场资料、单一来源完整引文）不变。
- 诊断：被拒的阶段和它的调用在 `error_code` 里记录 `规则@字段路径:数字类别`（如 `unsourced_number@limitations[0]:digits`；类别为 digits / percent / chinese_numeral / fullwidth_digits，格式错误时为 schema 问题类型）。字段路径只含 schema 键名和下标，不记录模型正文、提示词、密钥、Cookie 或连接串；任务本身的 `error_code` 仍只记规则名。没有新增迁移，被拒的回答仍不保存、不导出。
- 页面：停止处显示阶段、规则和字段；对输出检查不通过的情况明确说明「不是密钥或账户问题，不需要更换密钥」，并说明继续会重新发送这一步，是一次新的计费调用，程序不会自动重发或修格式。
- 不变：单次发送、不自动重试、不换供应商或模型、预算公式、并发、日限额、租约、幂等与未知调用恢复规则、人工审核门槛。

这些改动让合规的回答有明确、可通过的写法，但**不能保证**真实模型一定照做；需要在测试站用一次单独授权的真实调用验证。

> 3.2（checks v3）取代了本节「无来源字段一律不写数字」的规则，并开始检查选题的差异点与难度说明；其余仍然有效。

已知后续事项（本轮不做，均不放宽检查）：选题方向的一句话故事不做数字检查（差异点、难度说明自 3.2 起检查）；排名名次的中文与阿拉伯数字不互认（资料写「排名第三」不能支持「排名第3」，只会多拒不会误放）；含「热度、人气」的分句里故事序数也按名次处理（同样只会多拒）；冻结的版本号目前只是记录，没有按版本分支的提示词与检查。结构序数的单位里有「次、个」，在不含排名用语的市场分句里「第一个登上热门」「第三次登上热搜」这类说法仍不算数字（与修复前相同，不是新放宽）；「第二天」「第一手」「冒号后的第一，」等不在结构单位里的写法会按名次拒收（只会多拒）。

### 3.2 按数字含义判断（2026-10-20，prompt.v3 / checks.v3）

**证据边界**：线上任务（runId `47d81a9c-…`，DeepSeek / deepseek-flash，1 集、60 秒、0 轮、预算 6、资料有限）在研究阶段被 `unsourced_number@hypotheses[0].statement:chinese_numeral` 拒收，只发送 1 次。被拒回答按设计没有保存，所以**触发的原句仍不知道**，不能断定是模型编造统计还是检查误伤。能从源码确认的是：v2 对所有无来源字段「一律不许有数字」，于是「两个互不信任的人」「三次误会」「计划比较两个版本」这类合成样本（`packages/domain/src/auto-creation-semantics.spec.ts`，均为合成样本、非线上回答）都会被拒；同时 v2 还放过了「约 三 成」「H13 成」「十几万」「三千观众」「五百用户」「上万」「过万」等写法（修复前在旧代码上实测通过）。

**规则**（`packages/domain/src/auto-creation-numbers.ts`，确定性，不额外调用模型）：

- 有引用的文字（facts、observations、带 sourceIds 的 audience；research.v1 里带 sourceIds 的 contentStructure，自 3.3 起改为只核对 reference.quote）：不变，每个数字必须作为完整数字出现在所引资料的摘录正文里。
- 无引用的文字（hypotheses 的 statement 与 howToVerify、opportunities、limitations、appliedConstraints、不带 sourceIds 的 audience、contentStructure 的 application（3.3 起不论有无 reference），以及选题的 differentiation、difficultyNote、audienceFit）：数字按它数的是什么判断，**与字段名无关**：
  - 允许：冻结的集数、每集时长、人物/地点上限（只在非市场分句）；作品内序数；创作数量（人物 ≤ 冻结上限或 8、地点 ≤ 冻结上限或 6、反转/误会/伏笔/版本等 ≤ 30）；虚构人物年龄（有主角/角色等主语、非年龄段、非市场分句）；故事内时长（秒、分钟不超过每集时长）；验证计划的天数（≤ 90 天）；用户在硬约束里填写的目标观众原文，但只在写成创作目标时（见下）。
  - 拒收（`market_statistic`）：百分比/成数/比例词（翻倍、半数…）、万亿/倍/人次、名次、观众或用户数量、受众年龄或年龄段、市场分句中的平均值和频次、观看时长与集数。
  - 拒收（`result_claim`）：「数据显示 / 调查发现 / 已测试 / 测得」等写成已得到结果的数字；以及句中提到观众或市场、带了创作或计划数量、而观众或市场那一分句本身没有「是否、可能、待验证、计划、拟、上线后…」等待验证标记的判断（见下「标记的作用范围」）。
  - 拒收（`constraint_violation` / `frozen_conflict`）：创作数量超过冻结的人物、地点上限，集数与冻结值不同，时长超过每集目标。
  - 拒收（`unclassified`）：没有创作或计划含义的数字（日期、资料条数、超范围计数）。
- 一律先去掉空白和零宽字符、统一全角百分号再判断（「三 成」=「三成」）；编号只认 schema 允许的写法（H13 不是编号）；数字与单位之间的「多/余/来」不影响识别（三十多万、两千多名）；中文数字加 %、万分之、九零后/90后、「N 个 X 里 M 个」「三比一」都按统计处理。观众或市场用语与「数据显示 / 测过 / 投放过 / 胜出」等结果用语按**整句**判断（逗号前后都算）；在观众或市场句里，没有量词的中文数字（「完播率约七十」「二十五到三十五」）也算数字。标记为「假设」「计划」「建议」不豁免统计。被拒不会删改、截断或替换模型回答。
- 待验证标记包括「是否、可能、待验证、计划、拟」等，以及验证计划动词「对比、统计、收集、邀请、观察、试看、上线后」。
- **标记的作用范围**（PR #80 终审后修正）：观众、市场和结果用语按整句识别，但待验证标记只对它所在的分句（逗号隔开的部分）生效，不跨逗号替别的判断解锁。提到观众或市场、或写观众偏好与反响（更喜欢、偏爱、爱看、买单、买账、追捧、反响、口碑、受欢迎、最吸引…，以及版本之间的高下「…版本口碑最好」「…版本胜过…」）的分句是一个判断，必须自己带标记；写了偏好的句子即使没有观众用语也按观众句判断（「大家更喜欢三次反转的剧本」「三次反转的剧本口碑最好」被拒）。两种情况不算偏好判断，且都只在很窄的写法下成立：人物自己的喜好或名声，人物（主角、女主、反派、她、他；「她们、他们」指观众，不算）紧挨着喜好词、分句里没有版本/剧本/剧情/设定和观众用语（「女主爱看言情小说」「她在村里口碑很差」；「女主三次反转的版本口碑最好」仍被拒）；计划要收集或比较的反响，反响词是分句的最后一个词（「收集观众口碑」「比较两个版本的观众反响」；「收集到的观众口碑最好的是…」「上线后…口碑最好」「记录显示…」仍被拒）；写观众偏好的分句只认「是否、可能、待验证、如果、哪个…」这类存疑标记（「哪个」只在「看、比较、对比…哪个」这样由计划提出的问题里算；「不可能」「无论哪种…都」「哪个版本都…」和没有提问的「哪种结尾观众最终还是更爱…」不算），同一分句里的「计划、拟、上线后、对比」等计划用语不算（所以不加标点、用冒号、顿号、破折号、括号拼在一起也一样被拒）。数量在只讲故事或计划的分句里时，这一分句自己的标记可以覆盖它，但句中不能有未存疑的偏好判断；分句自己没有标记时，句中每个判断分句都要有标记。所以「计划比较两个版本，观众更喜欢三次反转的剧本」「计划观察七天，观众已经喜欢三次反转的剧本」「拟比较两个版本，观众更喜欢反转多的剧本」「上线后观众更喜欢三次反转的剧本」「三次反转的剧本反响最好，观众是否买账待验证」被拒（`result_claim` / `unmarked_audience_judgement`）；「待验证观众是否更喜欢两次反转的版本」「受众是否喜欢这种结尾，计划比较两个版本后再判断」「计划上线后观察七天，再比较两个版本的反馈」「主角经历三次误会，观众是否买账还待验证」「面向成年观众，计划比较两个版本」「上线七天后，计划比较两个版本的观众留存」可以通过。市场句中的天数只有带计划动词时才算观察期（天数所在分句提到观众或市场时，计划动词必须在同一分句；「可能三天内流失」不算）；市场句中的秒数只在「前/开头 N 秒」、不超过每集时长且按上面的范围有待验证标记时算作本集时刻。同一段文字里既有统计又有未标记的判断时，诊断先报统计。
- **冻结的目标观众**（PR #80 终审后修正）：用户填写的目标观众是创作选择，不是来源。原文只在写成目标时豁免：所在分句写明是目标（目标观众/用户/人群/受众、分句开头的「受众：」、面向、针对、适合、邀请、用户指定、拟定、用户约束、硬约束、用户设定），或分句里只有原文；括注只认「用户指定、用户约束、硬约束、待验证」等说明来源是用户的写法（「（问卷所得）」「（同类剧观众）」不豁免），且该分句没有「主要、核心、集中、为主、真实、实际」；整句没有结果用语（数据显示、调研确认、已确认…）和来源、平台、画像、多数、增长、消费用语（数据、调研、调查、统计、报告、后台、样本、行业、平台及抖音等平台名、画像、多为、居多、大多、多数、大部分、主力、最多、最常见、普遍、头部、增长、付费、舍得、占比…；「不是平台真实用户画像」「非平台统计结果」「不依赖真实平台数据」这类否认不算；另起的计划分句里只有数据、统计、平台、投放这类说明计划在哪里做的词时不算，如「计划在平台投放两个版本」「计划收集两个版本的观看数据」；主力、最多、占比、头部、付费、消费、调研等多数与画像用语在任何分句都算，如「拟抢占这一付费最多的人群」「计划沿用调研里的主力人群」被拒）。否则原文里的数字照常判断。冻结受众为「25-35岁的女性」时，「数据显示，本平台的受众主要是25-35岁的女性」「已通过调研确认，核心受众为25-35岁的女性」「本平台的受众主要是25-35岁的女性」「根据调研，目标观众是25-35岁的女性」「目标观众为25-35岁的女性，她们普遍爱看逆袭剧」被拒；「抖音受众：25-35岁的女性」「受众：25-35岁的女性居多」「25-35岁的女性（问卷所得）」也被拒；「拟面向25-35岁的女性创作，尚待验证」「目标观众：25-35岁的女性（用户指定）」「受众：25-35岁的女性」「拟面向25-35岁的女性创作，核心冲突是职场逆袭」「邀请25-35岁的女性试看两个版本，收集反馈」可以通过。所有无来源字段（含受众、选题的差异点、难度说明、受众契合）同样适用。
- 虚构年龄须紧挨人物（「主角二十八岁」），或后面是「的 + 非受众人群」（「30岁的单亲妈妈」）；「二十多岁的女性」「25岁的她们」按受众年龄拒收。「两个版本的评论」计数的是「的」前面的作品名词。
- 已知会多拒的写法（不放宽，均由合成样本确认）：与观众写在同一句、未标待验证的创作数量（「两个让观众意外的反转」）；故事金额（「欠下五十万」「一百块钱」）；计划中的样本人数（「邀请 5 位目标观众试看」）；「最多两个」这类没有名词的计数；提到市场的句子里的资料条数按市场统计报类别；提到观众的分句里的天数，计划动词却写在另一分句；与未存疑的偏好判断同句的创作数量（「观众爱看逆袭，两次反转的设定可能更有张力」），以及先写偏好、再在另一分句说待验证（「观众更喜欢三次反转的剧本，是否如此待验证」）；人物喜好词本身是市场用语时（「主角爱看小说，三次反转是故事核心」，修复前同样被拒）；故事里的付费、会员等市场用语让整句按观众句判断（「面向25-35岁的女性，主角是付费会员，经历两次反转」）；计划收集的对象太长、超过 12 个字（「计划比较三次反转与两次反转版本的观众反响」）；照抄冻结受众时同一分句用了「核心、主要」等用语，或整句出现「平台、数据、付费」等用语（如「拟面向25-35岁的女性，不依赖平台数据」）。

**诊断**：阶段与调用的 `error_code` 为 `规则@字段路径:数字写法+判断类别+子规则`，如 `unsourced_number@hypotheses[0].howToVerify:percent+market_statistic+proportion`，只含 schema 字段和固定标识，不含模型正文、提示词或密钥；任务本身仍只记规则名。v2 的旧码（无 `+`）照常解析显示。页面写出位置、数字写法、判断类别和子规则，并说明「这不说明模型一定编造了数据，也可能是写法让程序无法确认它是创作设定」「不是密钥问题，不需要更换密钥」。

**页面与剧本包**：资料有限时明示「受众和题材判断都是待验证的假设，验证计划尚未执行；不是实时市场验证，也不是平台真实用户画像」；事实、观察、假设与验证计划、目标观众、机会、局限、采用的约束分开显示。

**版本兼容**（历史，3.2 当时的规则；当前版本见 3.4）：当时新任务冻结 `prompt.v3` / `checks.v3`；类型同时接受 v1、v2。开始请求重放沿用已存任务自己的版本比较哈希（PR #79 机制），v1、v2 任务原键原请求返回 200，不新建、不调度、不发送，不改冻结输入和哈希。与之前一致，旧任务续跑时之后发送的阶段使用当前（v3）提示与检查，已完成阶段不重算。研究输出 schema 未改，无迁移。

### 3.3 内容结构：参考方法原文与本剧应用设计分开（2026-10-20，prompt.v4 / checks.v4 / research.v2）

**证据边界**：线上任务（runId `5718d519-71f5-4b11-a330-caa73fa71a3e`，DeepSeek / deepseek-flash，1 集、60 秒、0 轮、预算 6、`researchFetch=false`、资料有限）的研究阶段收到正常模型回答，被 `unsourced_number@contentStructure[0]:chinese_numeral+unsourced+not_in_cited_excerpt` 拒收。被拒原文按设计没有保存，**具体数字和原句仍不知道**，不能断定是模型编造。能从源码确认的是契约本身的缺陷：research.v1 的 contentStructure 是 `{pattern, why, sourceIds}`，一旦带引用，pattern 和 why 整体按来源内容核对数字，于是「借鉴某个方法、再为本剧设计两次反转」无法表达。合成复现（非线上原文）：pattern「计划用两次反转推动主角主动选择。」、why「这是本作品的创作设计。」，sourceIds=[S-KB-CRAFT] 被拒「两次」，sourceIds=[] 通过；在 main（14758ea）上用完整 `validateAutoStageOutput` 复现。

**新结构**（`autoContentStructureSchema`，Zod 与供应商 JSON Schema 同源、由测试核对一致）：

```
contentStructure: [{ reference: { sourceId, quote } | null, application: { pattern, why } }]   // 1–6 条
```

- **reference 是实际读到的方法原文**：sourceId 必须是本任务快照里已读取的资料（不存在 → `unknown_source`，未读 → `unread_source`，字段 `contentStructure[i].reference.sourceId`）；quote 去掉空白后 6–80 字，必须作为连续片段完整出现在**这一条**资料的摘录正文里，不能编造、改字、跨资料或在同一资料里跨段拼接；两端也不能切断数字：以数字（或紧跟数字的分隔符，如「,800」「-35」）开头时前面不能紧接数字、字母或数字间的分隔符（句末与分句标点以外的任何符号，以及「至、到、比」：「1,800」「25-35」「25－35」「1/3」「3：1」「25至35」「3比1」）；以数字结尾时必须正好停在摘录的句末或分句末（后面是句号、分号、顿号、冒号、括号、引号、空白，或后面不跟数字的逗号）；以紧跟数字的分隔符结尾（「约1,」）时后面不能还是数字（从「一百八十」截出「八十」、从「160秒」截出「60秒」、从「二十一次」截出「一次」、从「七成」截出「七」、从「1,800」截出「800」、从「10w」截出「10」、从「90后」截出「90」都拒收，`evidence_not_in_source@contentStructure[i].reference.quote`）；quote 里的数字再按完整数字与该摘录比对，这一步**不**豁免任务自己的集数、时长或「一次」这类冠词（`unsourced_number@…reference.quote:…+unsourced+not_in_cited_excerpt`）。
- **application 是本剧的原创设计**：不论有没有 reference，都按 3.2 的无来源文字检查：本剧的人物数、反转次数、虚构年龄、故事期限等创作数量可以写，**不要求出现在 quote 里**；冻结的集数、时长、人物和地点上限照常约束（`constraint_violation`）；观众比例、人数、排名、写成已得到结果的观众结论照常拒收，引用的资料里即使有同一个统计也不能替 application 提供来源。另外 application 里不带数字、但写成已得到的观众或市场结论（「调查证明观众更喜欢反转」「已验证这类结尾受欢迎」「经过调研，观众偏爱…」「据统计…」「实践证明…」「业内公认…」）也拒收（`unsourced_claim@contentStructure[i].application.pattern|why`）；「据统计、业内公认」本身就是市场说法，不需要另有观众用语（「业内公认这种结构最有效」被拒）。判断前先去掉空白和零宽字符；只有分句在结果用语之前**只写了**计划或假设用语（计划、拟、打算、准备、将要、如果、若、假如、假设、设想；前面可以有「我们、团队、本剧、制作方」，后面可以有「在…后/前/时」）时才算待验证（「计划通过试看验证…」「我们计划…」「拟在上线后通过试看验证…」「若数据显示…，再…」可以）；其他词里恰好含有这些字（「期待的…」「女将军题材…」「若即若离的感情线…」），或这些字出现在结果用语之后（「…准备充分的主角」），都不算。分句里结果用语前面**只有**人物（主角、女主、反派、她、他…，可带「的」）、结果用语是「调查…」、且整句里发现的内容（包括逗号之后）不涉及观众、市场或偏好时是剧情（「主角调查发现站长在说谎」「主角的调查发现站长伪造账本」「女主的调查发现邻居隐瞒了身份」可以；「主角的调查发现观众偏爱反转」「主角的调查证明这种结构有效」「她的调查证明这个故事最感人」（发现的内容说到作品自身的结尾、结构、故事、反转、人设、节奏、设定，或带「有效、有用、感人、抓人、好用」等只表评价的词，或有评价结构，都按对作品的结论处理。评价结构按位置判断，不按单字出现在哪里：程度词（最、更、更加、很、太、够、极、挺、非常、十分、特别、相当…）前面在同一分句里已有主语、处在谓语位置时算评价（「这招很灵」「先抑后扬更胜一筹」「上述手法最具感染力」「先抑后扬更加精彩」）；在发现内容的开头，或后面是数量、时间（更多、最后、最早、最先…）时不算，但开头的「最…的是、更…的是」算（「最妙的是先抑后扬」）；「超、真、蛮、颇」只在紧接「好、灵、妙、棒、赞、精彩、厉害、出彩」时算；分句以「灵、妙、好、棒、成功、好用、管用、奏效」（可带了、啊、吧、呀、的、呢、嘛、哉）或「绝了」结尾时算（「该招灵」「其手法妙」「反派越狠越好」「这种做法成功了」）；「妙不可言、灵得出奇、妙极了」这类延续以及灵验、精妙、绝伦、灵招等评价词也算。普通词里的单字不算，「主角调查发现好友伪造账本」「…发现灵堂暗藏机关」「…发现更多线索」「…发现更衣室藏着证据」「…发现站长此后改了名字」「主角的调查发现了真相」「…发现这封信是伪造的」可以通过）「观众对主角的调研证明…」「主角的数据显示…」「她调查发现观众更喜欢反转」「他调查发现，观众更喜欢反转」「其他调查发现…」仍被拒）；「据统计、业内公认」不受此例外影响。这一条只加在 application 上，其他无来源字段不带数字的说法仍与之前相同、不检查。市场事实只能写进 facts 和 observations。
- **reference = null**：没有合适的方法资料时允许自主设计，页面和剧本包显示「参考方法原文：无（自主创作设计）」。
- 错误的引用让整份回答拒收，检查不会删除引用、改成 null 或改写任何内容后放行；被拒回答不保存，后续阶段零发送。
- 人物数量的相关修复（只做本契约需要的部分）：数量词后面紧跟常见职业或身份词（骑手、司机、室友、邻居、房东、学生…，有限列表）时按人物计数（「三名骑手被迫合作」「两个室友互相猜疑」），受冻结人物上限和 8 人上限约束；在提到观众或市场的句子里按观众人数拒收（「三名学生观众更喜欢反转」）；同一分句里这些人在给出评价时是转述的反馈，不是人物，按已得结果拒收（例外很窄：「好评、差评、高分、低分」作名词，紧跟在「因、因为、由于、遭遇、遇到、收到」之后，中间至多是「一条、一则、恶意、匿名、顾客的…」这类固定修饰，后面紧接「后、而」或「联手、决定、反目、追查、寻找、报复…」这类剧情后果、且从评价词往后没有「看、追更、付费、充值、买单」时，是发生在人物身上的事，不算他们给的评价：「三名学生因一条差评联手追查真相」「三名骑手遭遇恶意差评后决定寻找证据」可以通过；「三名学生看过剧本后都给了好评」「三名学生被邀请试看后打了高分」「三名学生收到剧本后好评不断」「三名学生因样片好评」仍被拒）：评价本身（好评、差评、高分、打分、点赞、叫好、说好看、都说好、一致推荐、称赞…，如「三名学生都给了好评」「五名学生都说好看」「三位老师一致推荐」），或较弱的评价用语（夸、认可、推荐、满意、都说、都觉得、都认为、都用、都在用、买单、爱看…）同时指向作品或写法（结尾、结构、开场、版本、剧情、题材、本剧、这种、这类、这个…，如「三个记者都夸这个结尾」「五名主播都用这种开场」「三位老师都觉得结尾不错」「八名学生试看后都说结尾好」）；故事里的人物照常可以认为、一致决定、表示、互相推荐、说好、喜欢、采用，句子也可以提到本剧或某种方式（「两名警察认为主角是凶手」「两位房东都表示不知情」「两个室友说好一起逃跑」「两个女孩都很好看」「本剧让两名学生喜欢上同一个人」「三名骑手采用这种方式逃脱」可以通过；「三名骑手都觉得这种开场不对」这类人物对作品用语的看法会被拒，只会多拒）。评价用语是有限列表，表外的说法（「五位宝妈表示结尾很好」）仍按原规则判断。不在列表里的词照旧（「八名试映嘉宾都给了好评」「三位专家一致推荐」「三个骑士」「两位母亲」都按没有对应含义的数字拒收；3.4 起前两句按已得结果拒收，「三个骑士」「两位母亲」改为未核实提示）。没有改写全局语言规则，也没有扩张全局数字黑名单。

- **多拒**（合法写法被拒）：quote 必须与摘录逐字一致（只忽略空白），标点或繁简不同会被拒；以数字字结尾、却没有停在句末或分句末的 quote 都会被拒，即使最后一个字只是普通词里的「一、十」等；quote 以「第3」这类序数结尾时可能被当作名次拒收；先写结论、后写「是否…待验证」的句子会被拒；「事实证明最受欢迎的店员才是真凶」这类故事句因「受欢迎、事实证明」会被拒；职业词表是有限列表，表外的词仍按原规则判断（「三个骑士」「三名骑士」「两位母亲」会被拒为没有对应含义的数字；写「三个人物」可以通过）；剧情评价的例外只认固定的原因词、修饰和后果词，其他写法的剧情评价会被拒（「三名骑手被顾客打了差评后联手报复」「三名骑手因一条莫名其妙的差评被停职」「三名学生考了低分后被罚留校」）；人物调查的例外只认分句开头就是人物（「后来主角的调查发现…」会被拒），发现的内容里出现剧本、设定、结局等作品用语或任何评价用语时也会被拒（「主角的调查发现站长篡改了剧本」「主角调查发现这把刀很锋利」「主角调查发现站长很害怕」「主角调查发现站长此后更加小心」「主角调查发现站长躲进更衣室」「主角调查发现站长的病好了」「主角调查发现这个人很可疑」「主角调查发现凶手很狡猾」「主角调查发现站长最好的朋友是凶手」「主角调查发现邻居与站长有冲突」「主角调查发现站长拿到了绝招」（绝招、妙招、高招、灵招按评价词处理））；剧情评价的后果里出现「看」会被拒（「三名店员因一条差评而看清老板」）；3.2 已有的多拒照旧，例如「通过试看验证观众是否更喜欢两次反转」里的「通过…试看」被当作已测得的结果（各无来源字段相同，本轮未改）。
- **漏检**（应当拒收却会通过；除注明为本轮例外的词表外，均为既有词表边界，本轮不修）：application 的无数字结论检查只认「数据显示、调查证明、已验证、经过调研、据统计、实践证明、业内公认…」这类结果用语，「试看结果是…」「数据说明…」这类不在列表里的结果写法不拒；不带结果用语、也不带数字的观众判断（「观众更喜欢结尾反转」「爆款短剧都用这种结构」）与其他无来源字段一样不检查（与之前相同）；数量词后面是表外的人（「五位宝妈表示结尾很好」）仍按原有规则判断，修复前同样通过；评价用语同样是有限列表，表外的评价写法不拒；人物调查的例外判断「发现的内容是否在评价作品」也靠作品用语、评价词的有限列表和上面按位置判断的评价结构，表外说法不拒（不含上述作品用语、评价词，也没有谓语位置程度词或评价结尾的作品结论，如「主角的调查发现开门见山效果显著」「主角的调查发现先抑后扬有感染力」「…开门见山更多人爱」「…先抑后扬屡试不爽」「…这种手法尤其出彩」「…先抑后扬更早见效」「…最妙之处在于先抑后扬」「…最灵的一招是先抑后扬」「…更好的办法是先抑后扬」（开头只认「最…的是、更…的是」）「…这招灵哦」（不在列表里的语气词）；结尾是「强、狠、爽」或不带「了」的「绝」的评价也不拒，因为故事句常以这些字结尾，如「站长比他强」「站长下手狠」）；形如资料编号的「S-X-70%」会在读数字前被当作编号去掉（各无来源字段都如此，修复前已有，本轮未改）。

### 3.4 研究关卡：用户设定与资料局限由服务端记录，无法判定的创作数字改为未核实提示（2026-10-20，prompt.v5 / checks.v5 / research.v3）

**证据边界**：线上任务（runId `eb5632cc-4e15-4784-b7eb-c9be316fb335`）的研究阶段被 `unsourced_number@appliedConstraints[1]:chinese_numeral+unclassified+no_role` 拒收。被拒正文按设计没有保存，**原句仍不知道**；`no_role` 只说明程序没能判断这个中文数字数的是什么，**不能**据此认定模型编造了市场数据。合成复现（非线上原文）：在 main（2d2679a）上用完整 `validateAutoStageOutput`，「主角只剩五十元，必须当晚讨回工资。」放在 hypotheses、「失踪者留下三块拼图，逐集拼出真相」放在 application、「主角只剩五十元」放在 appliedConstraints，都被拒为 `…:chinese_numeral+unclassified+no_role`；同时模型自己写的 appliedConstraints 被照单接受。

这是一次明确的**产品门槛调整**：可追溯的事实、引用和硬约束照旧严格；程序判定不了含义的创作文字不再等同于不实市场数据，可以带着明确的「未核实」提示继续产出 DRAFT。

**模型回答与服务端记录分开**（`autoResearchAnswerSchema` / `AutoResearch`）：

- 模型回答（research.v3）只含 facts、observations、hypotheses（含验证计划）、audience、contentStructure、opportunities。**不再**含 limitations 和 appliedConstraints。回答严格（strict）：模型多写 `appliedConstraints`、`limitations`、`serverRecord`、`unverified` 或任何其他字段都整份拒收（`invalid_output@<字段>:unrecognized_keys`；只有研究阶段的这四个服务端键会写进字段位置，其他多余键名属于模型正文，不记录）。页面对所有严格阶段的多余字段统一说明「模型回答包含契约不允许的额外字段」，只有研究阶段命中这四个服务端键时才补充「用户设定与资料局限由服务端记录」，不会先接受再静默删除、覆盖或纠正。供应商 JSON Schema 同步去掉这两个字段，由测试核对与 Zod 一致。
- 服务端在研究通过后另存 `serverRecord`（`origin: server_record`），按可信数据生成、**不经过**数字含义判断：
  - `settings`（`origin: user_setting`）：来自冻结输入：集数、每集时长，以及**设置了的**题材、目标观众（注明「用户指定的创作目标，不是平台用户画像」）、出场人物上限、地点上限、禁止题材、结局要求。未设置的上限不出现，不生成额外限制。
  - `material`（`origin: source_snapshot`）：来自本任务资料快照：资料模式、已读取的资料及读取范围、未读取的资料及状态与说明、缺失说明（即快照的 notes，含「没有视频画面或音频理解能力」「不是实时市场验证」）。
  - `executedWith`：这份研究实际使用的提示、检查和研究版本（旧任务续跑时如实记录当前版本，冻结输入不改）。
- `unverified`：服务端的未核实提示，见下。模型和客户端都不能写入（回答 strict；客户端没有写阶段输出的接口）。

**未核实提示的准确边界**（`uncitedNumberReading`）：

- 只针对无来源的**创作设计、假设、验证计划**文字：hypotheses 的 statement 与 howToVerify、contentStructure 的 application（pattern、why，不论有无 reference）、opportunities，以及选题的 differentiation、difficultyNote。
- 只针对 `semantic=unclassified` 且 `rule=no_role` 的数字（不在提到观众或市场的句子里，也不属于任何已识别的角色）。其他 unclassified 子规则（日期或范围 `date_or_range`、超范围计数 `count_out_of_range`）照旧拒收。
- 提示保存字段、数字原文、`semantic`、`rule` 和固定说明「程序未能判定数字含义，未核实」；模型原文**不删、不截、不改**。页面、剧本包和后续提示按条目位置称呼提示所在处（「第1条假设（H3）」「第1条假设（H3）的验证计划」「第2条内容结构的本剧应用设计」「第1条机会」），假设附上模型自己的编号，不从数组下标编造编号：研究只要求编号不重复，不要求与顺序一致（PR #82 终审修正）。选题方向沿用 D1、D2…，因为选题检查要求编号按顺序。
- **不提前放行**：遇到 no_role 后继续读完同一分句、同一字段和后面所有字段。之后出现的统计、受众人数、已得结果、冻结冲突、伪造或截断的引用、未读来源、`unsourced_claim`、资料有限下标为有来源的受众、重复编号、schema 错误等都照旧整份拒收（「主角只剩五十元。七成观众偏爱反转。」在 main 上只报到 no_role 就停下，现在继续读并以 `market_statistic+proportion` 拒收）。
- 有引用的文字（facts、observations、带 sourceIds 的 audience、reference.quote）和受众文字（不带 sourceIds 的 audience、选题的 audienceFit，整段按观众判断）没有这个提示：仍须来源或待验证标记。
- 不发起纠错调用，不阻断后续草稿，不自动重试。

**放宽前补上的保护**（审计 main 上所有只因 no_role 被拒的测试样本后发现：这些说法过去只是碰巧被 no_role 拦住，放宽后会漏过）：

- 明确写出的冻结上限：「人物/角色」「地点/场景/场地」后面紧跟限定词（最多、至多、不超过、上限、限制、限、共，可再带「为、是、：」），然后是数字，数字后至多一个人或地点的量词（个、名、位、人、处、间）就到分句结束（「地点最多 4 个」「场景不超过 4 个」「人物最多 5 个」「角色上限：5」）。这时按人物或地点计数，超过冻结上限是 `frozen_conflict`，不会变成提示。没有限定词的「场景为三块拼图散落在桌上」「角色为五十元奖金冒险」不是上限，数字按无法归类处理（PR #82 终审修正：最初版本只看前面的名词，会把拼图和金额算成地点或人物）。只用已有的名词和限定词，没有新增词表。
- 量词本身不说明计数的是人：「三位数密码」「两位小数」「三名骑士」「两位母亲」都只得到未核实提示，不按人物计数（PR #82 终审修正：最初版本把「名、位」一律当作人，人物上限为 2 时「主角破解三位数密码」被误拒）。明确的人物计数（人物、角色、人、已列职业）仍受冻结上限和 8 人上限约束。
- 没有对应含义的计数，只有当它确实在数评价的人时才按已得结果 `result_claim` 拒收：数字后面是数人的量词（名、位、个），且评价在计数之后（「八名试映嘉宾都给了好评」「三位专家一致推荐」「五位资深编剧都认为这种结构最抓人」）。「主角用五十元购买一条差评作为追凶线索」里五十元不是在数评价的人，差评是剧情道具，按未核实提示处理（PR #82 终审修正：最初版本只要同一分句有评价词就升级）。

**页面、Markdown、JSON**：研究区依次是有来源的事实、基于样本的观察、「AI 创作假设与验证计划（假设未经验证；验证计划尚未执行）」、目标观众、内容结构、「机会（AI 创作判断）」，然后是「用户设定与资料记录（来自用户设定和服务端记录，不是 AI 调研结论）」和「未核实提示」。带提示的条目原文后标「（含未核实数字）」，提示单独列出，每条写明「只属于创作假设或设计，不是有来源的事实或市场结论」；已选方向下单独列它自己的提示。资料有限模式仍明示不是实时市场验证。JSON 剧本包原样保存研究输出（含 `serverRecord` 与 `unverified`），并附 `research.identity` 说明每部分的身份。后续选题与设定提示把资料记录标为「服务端记录，不是 AI 调研结论」，把每条提示原样带上并说明不能写成事实、平台用户画像或已验证的市场结论；审阅提示不含研究内容。

**版本兼容**：新任务冻结 `prompt.v5` / `checks.v5`。research.v1、v2 原样读取、显示（局限与约束标为「AI 填写／AI 复述，历史版本」）、导出，不补造服务端记录。v1–v4 任务原键原请求仍返回原任务（零新建、零调度、零发送），冻结输入、哈希、输出、调用和费用不改；已完成阶段直接复用。旧任务显式续跑到未完成的研究阶段时使用 research.v3，并在 `serverRecord.executedWith` 如实记录，冻结身份不回写。历史被拒任务不会自动重跑。没有新增迁移（`serverRecord`、`unverified` 存在既有 JSONB 输出里）。

**已知边界**（合成样本确认，按约定不扩充词表）：

### 3.6 时长按所指对象区分：本剧篇幅、观看时长与无法确认的时长（2026-10-21，prompt.v7 / checks.v7）

**证据边界**：线上任务（runId `1af794d3-5a55-4a8b-b64b-d1f18a5b06ff`）的研究阶段被 `unsourced_number@hypotheses[0].statement:digits+market_statistic+viewing_duration` 拒收。被拒正文按设计没有保存，**线上原句仍不知道**，本节不猜测它。Codex 在当前源码上用完整 `validateAutoStageOutput("research", …)` 确认下列**合成样本**被误拒，本轮先在未修复的 main（b804437）上复现：三句都返回与线上相同的 `digits+market_statistic+viewing_duration`，「观众是否会在前3秒被吸引」通过。

1. 待验证观众是否喜欢本剧60秒的紧凑叙事。
2. 观众可能愿意看完本剧60秒的故事。
3. 待验证：观众能否在60秒内理解人物冲突。

**误拒原因**：提到观众或市场的分句不会移除冻结设定里的数字（「每天观看60秒」即使任务是 60 秒也是统计），所以句中的 60 秒进入时长判断；而旧规则在观众分句里只放行紧跟在「前 / 开头 / 开场」后的秒数，其他秒数或分钟一律判为观看时长，不看它指的是本剧还是观众的观看行为。

**三类时长**（只在提到观众或市场的分句里，秒、秒钟、分钟；`packages/domain/src/auto-creation-numbers.ts`）：

| 类 | 怎样识别 | 结果 |
| --- | --- | --- |
| A 本剧篇幅 | 时长紧跟在指本剧的词后（本剧、本集、这部剧、该剧、全剧、单集、整集、每集，可带「的时长 / 篇幅」「为 / 是」「约」），后面是分句结束、「的」「内」「篇幅」「版本」等；本剧指代前紧跟观看动词时（观看本剧、看了本集）只有时长后接「的 / 篇幅 / 时长 / 版本」修饰名词才算 A（「观看本剧60秒的故事」） | 按冻结设定检查：等于每集时长（「本剧 / 全剧」也可等于全部集数合计）才通过（`work_length`）；超过为 `frozen_conflict+over_length`，变短为 `frozen_conflict+length_changed`（整份拒收，`constraint_violation`）。数值等于冻结值**不能单独**豁免：不指向本剧的 60 秒照样按 B/C 判断；通过后观众分句仍须写明「是否 / 可能 / 待验证」等，否则按 `unmarked_audience_judgement` 拒收 |
| B 观看时长与测量结果 | 分句里有习惯或多数的说法（通常、一般、往往、普遍、经常、大部分、多数…）；时长前紧跟观看动词（观看、看了、看、播放、停留、刷…），包括观看动词以本剧指代为宾语、时长不修饰后面名词的写法（「观看本剧60秒」「看了本集60秒」「观看本剧60秒内」，PR #84 终审修正：本剧指代不豁免观看行为）；或时长后紧跟观众离开（后退出、后流失、就划走、弃剧…）。平均值与频次（平均、每天、人均…）和已得结果（数据显示、实测、已测试…）在此之前已由原规则拒收 | 硬拒，`market_statistic+viewing_duration`（或原来的 `rate_or_average` / `measured_result`）；写成「假设」「计划」「可能」也不豁免；与冻结时长相同也拒收 |
| C 无法确认 | 不属于 A、B，也不是开场时刻（前 3 秒）的时长：分句写明待验证（是否、能否、可能、待验证…），且不超过冻结的每集时长 | 在无来源的创作字段里原文保留，生成服务端提示 `semantic=unclassified`、`rule=duration_unconfirmed`、note「程序无法确认时长含义（不是已判定的观看统计），未核实」；没有写明待验证或超过冻结时长的，仍按 `viewing_duration` 拒收 |

- 「每集」后紧跟秒或分钟时是本剧的单位，不再当作频次（「本剧每集约 60 秒的节奏」）；这只豁免紧跟其后的那个时长；同一分句里的其他数字按它计数的对象判断：数的是具名的剧情事物（反转、误会、人物…）时「每集 + 时长」仍是本剧单位（「待验证观众是否喜欢本剧每集60秒内发生两次反转的故事」通过），只有量词的次数（观看 3 次、3 遍）仍把「每集」当频次（PR #84 终审修正：「假设观众会把每集60秒的故事观看3次」「…重复观看3次」按 `rate_or_average` 拒收）；「观众每集观看…」「平均每集…」仍是频次或观看行为。
- **适用范围**：与 3.4 的 no_role 未核实提示相同的无来源创作字段——hypotheses 的 statement 与 howToVerify、contentStructure 的 application（pattern / why，reference 有效或为 null 都一样）、opportunities、选题方向的 differentiation / difficultyNote；limited 与 sourced 两种契约一样。没有来源的 audience 文字和方向的 audienceFit 本来就整段按观众文字检查、没有未核实出口：A 照样通过，C 在那里以 `unclassified+duration_unconfirmed` 拒收（诊断写明是「无法确认」，不是「已判为统计」），B 照旧拒收。有来源的事实与观察的数字、来源和引文检查不变。
- **提示不提前结束检查**：C 只是记录，同一分句、同一句、后面的字段照旧逐个判断；之后出现「七成观众」、实测结果、平均值或冻结冲突，整份拒收。
- **身份**：C 提示不是校验为真，也不是市场结论。它和 no_role 提示存在同一个 `unverified` 列表里；后续选题提示、页面和 Markdown / JSON 剧本包都按「未核实提示」显示，各条用自己的 note。列表标题在含时长提示时为「程序未能判定数字或时长含义，未核实」，全是 no_role 时保持原来的「程序未能判定数字含义，未核实」，所以旧任务的页面和导出不变；旧 no_role 提示与旧拒收诊断照原样读取，不改历史记录。新拒收子规则 `length_changed`、`duration_unconfirmed` 在页面有对应说明，`viewing_duration` 的说明写明「观众实际看多久、看多久后退出」。
- **提示 v7**：数字规则第 2 条补一句：提到观众时写本剧时长，要写明是本剧的篇幅（如「待验证观众是否喜欢本剧 60 秒的故事」），不写观众实际看了多久、看多久后退出、通常或平均看多久。研究回答结构没有变化，research 仍为 v4，不重做契约；limited 仍只能回答五个根字段，模型不能填写 facts、observations 或服务端字段，不删除、截断或改写回答。

- **提示 v8**：limited 与 sourced 两种研究提示在各自的 hypotheses 说明之后加入同一组说明（`HYPOTHESIS_FIELD_LINES`，`packages/domain/src/auto-creation.ts`，两种模式共用一份，不会各自漂移）：hypotheses 是数组，1 到 8 条；每条是一个对象，只包含 `id`、`statement`、`howToVerify` 三个必填字段（id 为 H1、H2 这样的编号，statement 不超过 200 字，howToVerify 是将来的验证计划、不超过 150 字）；不要给假设添加任何其他字段（包括空值、空数组、备注或理由等解释性字段），多出一个字段也会整份拒收。另给一个只含这三个字段的假设对象示例，不含任何数字、市场统计或已得调查结论，示例本身通过 limited 与 sourced 的完整校验。limited 提示仍只要求它允许输出的内容，不出现 sourced 或服务端字段名。提示构建器其余部分不变。

- **影响范围**：共享研究提示同时用于原短剧 AI 自动创作的 research 阶段和系列编剧借用的 research 阶段（`SERIES_RESEARCH_CONTRACT.promptVersion` 跟随 `AUTO_CREATION_PROMPT_VERSION`）。新建的自动创作任务和新建的系列都冻结 prompt.v8；系列自身的 `ads.series-writing.prompt.v1` / `checks.v1` 不改号。
- **历史**：旧任务、旧系列的冻结输入（含 v7 及更早的版本号）、哈希、调用、输出和费用不回写；已完成的阶段直接复用；显式续跑后发送的研究使用当前提示，`executedWith` 如实记录实际执行的 prompt.v8，冻结版本保持原样。线上失败的作品与旧授权不修改。Migration 编写 0、执行 0。

**限制**：这只是格式引导，不保证真实模型每次遵从；离线验收全部使用合成样本与模型替身（替身的 `extra` 字段是合成样本，不是线上原文），**离线通过不等于线上成功**。真实模型是否不再添加多余字段，需要受限的真实验收确认。

### 3.8 验证计划里的样本集数与全剧总集数（2026-10-25，checks.v8；prompt.v8 / research.v4 不变）

**证据边界**：线上 prompt.v8 系列验收（60 集、每集 60 秒）首次 research 调用返回后被拒为 `constraint_violation@hypotheses[0].howToVerify:chinese_numeral+frozen_conflict+episode_count`。被拒正文按设计没有保存，**实际句子不知道**，本节不猜测、不声称还原了线上原文。已确认的代码事实：检查把文本里任何「N 集」（N 不等于冻结集数）都当成全剧总集数，所以冻结 60 集时，合成的验证计划「计划制作三集样稿进行试读并收集反馈。」「计划选取三集样稿进行试读并收集反馈。」「计划试读前三集样稿并收集反馈。」（以及阿拉伯数字写法）都被拒为 `frozen_conflict` / `episode_count`。

- **只在 `hypotheses[].howToVerify` 里**区分三类集数（`packages/domain/src/auto-creation-numbers.ts` 的 `verificationPlan` 选项，由 `auto-creation.ts` 只对 howToVerify 传入）：
  - **A 全剧总集数**：本剧规模或把本剧改成其他集数（「本剧共三集」「计划将本剧改为三集再验证」）仍须与冻结集数一致，不一致就拒收为 `frozen_conflict` / `episode_count`，带「计划」也一样。
  - **B 本剧的验证样本**：一个分句同时写明是计划（计划、拟、打算、准备）、写明要制作、选取、抽取、挑选、试读或试看，而且数字紧跟着「集样稿」或「集样片」时，这个数字才算样本，不算全剧总集数（「三集样稿」「前三集样稿」「第 2 集样稿」）。样本数量或位置必须在 1 到冻结集数之间，否则拒收为 `frozen_conflict` / `sample_out_of_range`（零集、六十一集、第 61 集）。原来被当成结构位置直接放过的「第 N 集样稿」，在这个验证计划路径里也按范围检查。分句里写了已执行（已、曾、试读过/了）、改动全剧规模（改为、改成、缩减、压缩、共计、总共……）或观看习惯（通常、一般、大多……）时，不算样本，仍按原规则判断。分句里出现观众、试看者，不会让样本计划变成统计，也不会自动放行。
  - **C 统计或已执行结果**：观看习惯、平均数、频次、比例、排名、已执行的测试结果仍按原规则拒收。识别出一个合法样本后，同一分句、同一句、后续假设和机会字段都照常检查，合法样本不会替后面的统计或总集数冲突解锁。
- **不变**：`statement`、机会、内容结构、受众等其他字段不获得样本豁免（同一句样本计划写在 statement 里仍拒为 `episode_count`）；没有放宽 strict schema，不删除字段，不自动修 JSON、重试、换供应商或模型；预算、日限额、幂等、租约、恢复、审核门槛、数据库结构都不变；不保存拒收正文，错误日志不扩大。研究提示没有改动，仍为 prompt.v8。
- **版本**：检查语义已经变化，`AUTO_CREATION_CHECKS_VERSION` 升为 `ads.auto-creation.checks.v8`（本仓库此前没有用过 checks.v8），历史类型保留 v1–v7。新任务冻结 checks.v8；新系列的 `researchContract` 冻结 checks.v8，`SeriesResearchContract` 允许旧系列保留冻结的 checks.v7。系列自身的 `ads.series-writing.prompt.v1` / `checks.v1` 不改号。旧任务、旧系列的冻结输入、哈希、调用、输出和费用不回写；之后实际发送的研究由 `executedWith` 如实记录 checks.v8。Migration 编写 0、执行 0。

**仍有边界**：判断按措辞，不理解语义。只认紧跟「集样稿 / 集样片」的样本写法；「计划试读前三集」（没有「样稿」）、「请试看者看完前三集」仍按原规则拒收；计划词与动作词是有限列表。离线测试全部使用合成样本与模型替身，**不证明线上原句就是这些写法，也不保证真实模型下次通过**。

### 3.9 样本动作必须带着当前数量（2026-10-25，checks.v9；prompt.v8 / research.v4 不变）

**根因**：checks.v8 只要求计划词和样本动作在**同一分句任意位置**出现，没有确认这个动作支配的正是当前「N 集样稿」。冻结 60 集时，以下两句合成样本在 1feb0a6 上都被拒收，在 fc64e84（checks.v8）上却无提示通过：

- 「计划选取观众看完三集样稿后都弃剧的案例。」——「选取」的对象是案例，「三集」是观众看了几集，应拒为 `unsourced_number`，`market_statistic` / `viewing_count`。
- 「计划把本剧缩至三集样稿后试读。」——这是改变全剧规模，后面的「试读」不支配「三集」，应拒为 `constraint_violation`，`frozen_conflict` / `episode_count`。

**修复**（`packages/domain/src/auto-creation-numbers.ts` 的 `sampleBound`）：数字前面必须紧接样本动作（制作、撰写、选取、抽取、挑选、选出、抽出、试读、试看），中间只允许「前」或「头」，并且计划词出现在这个动作之前，例如「计划制作三集样稿」「计划试读前三集样稿」「计划邀请观众试读三集样稿」。动作在分句别处时不给豁免，数字照原规则判断。没有逐个添加「缩至」「弃剧」这类黑名单，也没有改写整个分类器。中文、阿拉伯数字，样稿、样片，1 到冻结集数的范围检查，以及「第 N 集样稿」的越界检查都不变；样本放行后，同一分句、同一句、后续假设和机会字段照常检查；豁免仍只在 `hypotheses[].howToVerify`。

**版本**：`AUTO_CREATION_CHECKS_VERSION` 升为 `ads.auto-creation.checks.v9`（本仓库此前没有用过 checks.v9），历史类型保留 v1–v8。新任务和新系列的 `researchContract` 冻结 checks.v9，旧系列保留冻结的 v7 或 v8；之后实际发送的研究由 `executedWith` 记录 checks.v9。prompt.v8、research.v4、系列自身 prompt.v1 / checks.v1 不变。旧任务的冻结输入、哈希、已完成输出、调用和费用不回写。Migration 编写 0、执行 0。

**仍有边界**：仍按措辞判断。动作必须紧贴数量（只隔「前 / 头」），所以「计划制作约三集样稿」「计划选取其中三集样稿」这类写法会按原规则拒收；动作紧贴数量之后的内容（例如「样稿」后面再接别的宾语）不再分析。两条样本都是合成句子，不是线上被拒原文。

## 4. 质量检查与有限修改

- 程序检查（`deterministicFindings`）：缺集、场次上限（60 秒 ≤5 场，90 秒 ≤7 场）、台词字数（≈5 字/秒）、镜头计划秒数在目标 60%–140%、仅被提及的人物出场、禁止题材、全剧出场人物数和地点数上限、跨集重复台词（提示级）。问题按真实来源归属：设定本身的出场人物在生成时已核对上限，所以合法设定下的人物超限只能来自分集让「仅被提及」的人物出场，这时问题指向那几集，可以在已授权的轮次和预算内定向修改并复查；只有设定本身超限才算设定问题。schema、编号、悬空引用、硬约束（人物/地点数、禁止题材）、整理后超过编辑器 2 万字上限的分集在**生成时**就拒收（不截断）。
- AI 审阅：独立系统提示与评价标准；证据必须**完整出现在目标对象的某一个文字字段里**（只忽略空白），不跨字段、数组元素或对象拼接：台词接上它的语气说明（「签哪儿？」+「平静」）、设定里 desire 的结尾接上 weakness 的开头，都不算引文。找不到的问题保留展示但**不采用**（不阻塞、不驱动付费修改，也不会被判成无法修改的设定问题）。`reviewTargetText` 只用于展示。分数只作内部参考。
- **累计审阅输入预算**：每次审阅都要完整读到设定、大纲和每一集的当前版本，这些文本的 JSON 合计不超过 28,000 字符（`AUTO_REVIEW_CONTENT_BUDGET_CHARS`）；40,000 字上限中其余部分留给指令、用户约束、程序检查摘要（不超过 3,000 字）和上一轮问题，修改提示则留给指令和待解决问题。每份文本在写出前都有保证份额（设定 8,000；大纲 400+900×N；每集为剩余部分平分），实际更短时省下的部分可以给后面的文本用，但前面的文本不能占用后面文本应得的份额；修改版按替换原版计算。提示会告诉模型本步的长度上限；被接受的输出超出剩余份额时拒收（`too_large`，`review_budget`），**不截断剧本结尾**，也不跳过审阅、不增加调用。这样凡是被接受的成果都一定能进入必要的审阅和修改，正常调用次数不变。
- 程序检查摘要：审阅提示里的程序检查结果放得下就原样列出，放不下时按「目标 + 类型」合并计数并给一个例子，再放不下按类型合并并列出涉及的目标；**完整的检查结果仍全部保存在审阅记录里**，用于程序裁决、页面和导出。修改提示把同类检查结果合成一条并列出全部编号，每个编号仍可回应。复现用例：6 集、每集约 1,741 字符（2,261 UTF-8 字节）的合法剧本、235 条检查结果，旧提示 42,713 字超过上限、10 次调用后停在 `prompt_too_large`；现在审阅提示不到 30,000 字，按正常计划和两轮修改共 19 次调用完成。
- 通过条件由程序判定：没有高严重度的程序问题，也没有已核实的高严重度 AI 问题。模型自己的 verdict 只记录。
- 修改：默认最多 2 轮（可选 0–2），每轮最多改 min(N,3) 集，只改有阻塞问题的分集，然后整体复查。整轮调用必须在本任务预算内才会开始；轮次或预算用完仍不合格 → `quality = needs_work`（「待完善」），保留成果和具体问题，绝不改成通过。设定/大纲层面的阻塞问题无法靠改单集解决：只要存在这类问题就**不再花调用做修改轮次**，直接 `unrevisable_issues`；没有保存成功（例如故事超长）时也记录最终质量结论。
- 修改后，基于旧版本写成的后续分集标记「上游内容已修改，这一版需要复核」（`upstreamChanged`），旧版本标记被哪个版本取代。

## 5. 预算与供应商

- 正常调用：N+5（研究、选题、设定、大纲、N 集、1 次审阅）。最坏：N+5 + 轮数×(min(N,3)+1)。硬上限（含人工确认的 2 次续跑重发）：最坏 + 2。1 集默认：正常 6，最坏 10，上限 12。6 集：正常 11，最坏 19，上限 21。
- 用户可在 [正常, 硬上限] 内设预算；低于正常次数在页面和服务端（400）都拒绝，**不创建任务、不发送**。
- 每次发送前在工作区调用锁内原子预约：任务预算、工作区 24 小时上限（与标题创作、在线候选共用计数）任一不足即停在发送前。开始时还检查剩余次数 ≥ 正常次数，否则 429 且不创建任务。没有提高任何管理员限额。
- 每次输出上限 4096 tokens；实际请求在发送前仍按完整的系统提示和用户提示（含检查摘要、上一轮问题和修改信息）做最终校验，超过 40,000 字不发送（`prompt_too_large`）。上限没有放宽。
- 没有可靠价格：只承诺调用次数和 token 上限，`billing_status` 恒为 `unknown`。调用结果未知（state=unknown）与费用未知是两个字段。
- 默认供应商取后台实际配置；配置的默认不可用时 503 并说明缺项，**不改投**其他服务。任务冻结供应商和模型；DeepSeek 新任务写入 `providerAdapter` 标识，无标识的 DeepSeek 任务永不发送。

## 6. 持久化、幂等与恢复

- 表（迁移 `20261019000100_auto_creation`）：`auto_creation_run`（冻结输入、授权方式、预算、已用次数、修改轮次、质量、故事保存）、`auto_creation_stage`（每阶段输出、输出哈希、`depends_on_json` 依赖版本、剧本写入状态）、`auto_creation_call`（每次真实发送一行、usage、unknown 费用）、`auto_creation_resume`（续跑键与确认的不确定调用）。
- 开始：`Idempotency-Key` + 输入哈希（授权方式不计入身份）。同键同内容返回原任务；同键不同内容 409；比较身份时，同一工作区、同一操作者、同一作品、同一键的已有任务沿用它自己冻结的提示词和检查版本（服务端读取，请求不能提交），所以升级前开始的 v1 任务用原键原请求重放仍返回原任务（200），不新建、不调度、不发送，也不改写它的冻结输入和哈希；作品已有故事或已有自动任务 409，不覆盖。页面先把冻结请求和两把键写入会话存储并读回，刷新后只能原样重试。
- 执行：API 进程内按租约运行；已完成阶段绝不再调用；超时/断线/5xx/执行者丢失 → unknown，任务 `needs_attention`，**不自动重发**；续跑必须正好确认当前的不确定调用，续跑键重放只返回当前状态；冻结的调用预算已用完时续跑直接拒绝（`AUTO_CREATION_BUDGET_EXHAUSTED`），不重置任何阶段。所有阶段都已完成、只因故事整理后超过保存上限（`story_too_large`）而停止的任务是终态：再次整理只会得到同样的超长文本，续跑直接拒绝（`AUTO_CREATION_NOT_RESUMABLE`），拒绝前不写续跑记录、不重置阶段和任务状态，页面不再提供「继续」，剧本包照常可读可下载；真正可恢复的只差保存的情况（例如最后一步完成后、保存前被停止）仍可续跑，续跑只做保存、不发送。
- 续跑前的可继续性检查（`autoResumeBlock`）：续跑只把需要重做的阶段改回待执行，所以下一步的请求就是用冻结输入和已保存成果构造的那一个。构造出的请求超过输入上限时，续跑在写续跑记录、重置任何状态之前拒绝（`AUTO_CREATION_PROMPT_TOO_LARGE`，409），同一个键重试也一样，页面显示原因、不再提供「继续」；这不是把 `prompt_too_large` 加进终态列表（此时通常还有待执行阶段）。旧提示下停在审阅前、现在能构造合法请求的任务可以正常续跑，只发送审阅，前面已完成的阶段全部复用。重放已受理的续跑键、未知结果的确认、供应商配置缺失、只差保存这些可恢复路径不受影响。
- 研究读取能力变化：任务开始时冻结了 `researchFetch=true`，但服务重启后关闭了页面读取（没有读取器）时，资料阶段**不会**用空结果完成（那样参考网址会从来源记录里消失）：任务在资料阶段之前停下（`needs_attention`，`research_fetch_unavailable`），不发出调用，冻结输入里的参考网址和任务身份原样保留，也不会被标成已读。此时续跑返回 503 `AUTO_CREATION_RESEARCH_UNAVAILABLE`，不写记录、不重置；重新开启读取后可以续跑，从资料阶段继续，读取冻结的网址，之后每个阶段只发送一次。没有绕过关闭开关去恢复抓取。
- 页面的续跑身份：续跑键与这次请求确认的调用列表作为**同一个身份**按「作品 + 任务」保存在会话存储（不保存令牌、Cookie 或任何凭据）。没有收到结果（断网、网关错误、无法识别的回应）时，刷新或重复点击都只会原样重发同一个键和同一组确认，即使之后出现了别的不确定调用；只有收到任务结果，或服务端给出明确拒绝（说明未受理）后，才会为下一次续跑生成新身份。标题创作的续跑同样会避开正在自动创作的同一作品，并计入共用的并发上限。无效 JSON 等明确拒收 → 停止，不追加修格式调用。
- 重启：维护循环 15 秒一次，只接管租约过期的任务；已预约未发送 → 安全重来，已提交 → unknown。开关关闭时只做隔离（fence），不发送。

## 7. 自动完成与人工审核

- 运行记录 `authorization`：`mode=auto`、`proof=site_session|operator_token`、`initiatedBy`、`executor=auto-creation-engine`（服务端写入，客户端无法携带）。
- 完成后通过受控入口把故事存为 **DRAFT** 故事版本，正文首行写明「AI 自动创作草稿｜机器生成，机器质量检查不等于人工审核」，`created_by = auto-creation:<runId>`（机器身份，不冒充人）。作品已有故事 → `story_conflict`，不覆盖，剧本包照常可下载。
- 剧本写入分集仍要求**人工审核通过**的当前故事（沿用原审核和写入门槛），并且剧本包必须完整（所有阶段包括最终审阅都已完成）；本任务生成的故事必须确实已经保存进这部作品（`storySave=saved` 且原故事版本存在），否则拒绝（`AUTO_CREATION_STORY_NOT_SAVED`，零分集写入、零内容修订）——故事超长没保存、或作品里已有人的故事（冲突）时，生成的分集剧本不会挂到另一份审核通过的故事上；「确认审核时改过故事」只用于确认已保存故事之后的版本变化，不能代替原故事存在；续跑和开始一样，不会与同一作品上的标题创作同时进行；一次写入全部分集的当前版本，已有剧本的分集记冲突不覆盖，重复写入不产生新版本。
- 返回入口：作品页面（`/projects/<id>/create`，也是「我的作品」里打开作品的页面）在标题下方常驻「回到 AI 自动创作任务」，故事已保存、剧本还没写入时提示「故事人工审核通过后，回到任务里把分集剧本写入作品」。入口只读取作品已有的任务（`GET …/auto-runs/latest`），不创建任务、不续跑、不调用模型；作品没有任务或读取失败时不显示。刷新、重新登录或直接打开作品都能找到。任务页的「去作品中人工审核故事」直接打开故事一步。
- 页面分开显示：剧本包、机器质量检查（内部参考）、人工审核、视频成片，并逐集显示「已写入 / 已有剧本未覆盖」。剧本包的人工审核字段只在剧本已按人工审核通过的故事写入后才记为通过。完成不等于允许发布。
