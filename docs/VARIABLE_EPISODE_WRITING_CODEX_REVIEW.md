## 问题、证据与修复

### R1 — P1：旧代码回退条件不足以保护新规格数据

- 文件：`docs/VARIABLE_EPISODE_WRITING_IMPLEMENTATION_REPORT.md:173`。
- 触发：按照旧说明，在“当前没有 running v2”时退回旧 API/Worker，并恢复业务写入。
- 影响：暂停、结果未知或已取消的 v2 任务仍可能由旧续跑接口驱动；旧启动接口也可能给新规格作品创建三集任务。即使标题创作关闭，旧故事审核仍会补建 1–3 集，旧 Mock 批次规则也不认识非三集规格。
- 证据：基线 `7222248` 的 `title-writing.service.ts` 启动/续跑不检查新项目规格与输入版本；旧 `title-writing-engine.ts` 使用三集提示词。旧故事审核建集逻辑固定三集。因此“无 running”不是安全回退条件，“关闭标题创作”也不是全站写保护。
- 最小修复：文档明确已有带规格作品/v2 数据时不得退旧 API/Worker 后开放写入，优先 forward-fix；必须回退则保持维护隔离，停止写入执行者，不清数据、不执行向下迁移。未宣称仓库存在已验收的维护只读模式。

### R2 — P2：全流程额度预检改变了历史 v1 启动行为

- 文件：`apps/api/src/studio/title-writing.service.ts:208`。
- 触发：新建 v1 任务，当日剩余额度为 1–4 次。
- 影响：R1 原实现提前返回 429，违背 v1 按原逐次预约规则工作的兼容承诺；这个收紧没有被确认为产品决定。
- 证据：新增 API 回归在原实现返回 429，期望 201，退出码 1。
- 最小修复：N+2 启动预检仅用于 v2。修复后 v1 剩余两次仍能启动，只发送两次便按原规则进入 partial；不会超额，同键重放不新增任务/发送。v2 不足额度仍是零 run、零 step、零发送。

### R3 — P2：旧编剧助手仍向不支持的规格提供入口

- 文件：`apps/web/src/components/workbench.tsx:463,585,882,1065`；新手提示在 `beginner-flow.tsx:693`。
- 触发：非三集作品使用故事助手，或第 4–6 集使用分集助手。
- 影响：故事助手固定三集策划，分集指令构造器只接受 1–3；页面会提供不符合当前规格的策划或只能报错的操作。
- 证据：新增 12 个组件用例在基线 8 失败、4 通过；修复后 12/12。既有写作助手测试覆盖历史无规格作品。
- 最小修复：不挂载不支持的助手，显示清楚的范围说明；工作台和新手流程共用此限制。保留正文编辑、来源检查、幂等、版本保存，测试核对手动保存路径/内容及回执。没有将这组模拟 API 测试称为真实落库证据。

### R4 — P2：重放被拒不代表此前没有模型调用

- 文件：`apps/web/src/components/title-writing-start.tsx:119`。
- 触发：第一次启动已被服务端受理但回执丢失，随后原键重试遇到 403 或 409。
- 影响：原页面会声称作品为空、任务未创建、没有任何模型调用，可能误导用户对重复创作和计费的判断。
- 证据：两个新用例模拟首次受理但丢回执，原实现 2/2 失败；修复后通过，并核实原 projectId/runKey/请求正文保留、没有自动创建第二个任务。
- 最小修复：普通拒绝只描述本次请求，明确此前未确认请求可能已经执行，建议查看进度。只有在幂等查询后明确返回额度不足的分支，才说明本次没有创建新任务/调用。未改重试和幂等逻辑。

### R5 — P2：锁竞争验收失败时可能无法释放持锁连接

- 文件：`packages/database/src/episode-plan.acceptance.spec.ts:220,238,344,486`。
- 触发：`createRun` 将来回归为等待测试持有的 call lock。原测试直接 await，Vitest 超时不会取消 SQL；finally 无法及时释放 holder，afterAll 的 pool.end 同样无界。
- 影响：该验证最需要报告失败时反而可能挂住，丢失失败证据。
- 最小修复：操作和收尾各自有界；排队 Promise 立即处理拒绝，finally rollback，失败则销毁 holder，再等待队列结算；保留原始失败，证据先写，连接池关闭也限时。
- 新增三项隔离 PostgreSQL 故障场景：业务体抛错、确认真实锁等待后超时、holder 销毁。用 pg_blocking_pids 确认等待，不以固定延时冒充锁交错。
- 本地只做专项 TypeScript、ESLint 检查，均退出码 0；未连接数据库。这三项的真实结果必须看本修复提交的隔离 CI。

### R6 — P2：人物保存测试没有等待保存完成也能通过

- 边界：没有独立重现旧 CI 那次缺失 heading 的精确故障，不能断言已经证明其唯一原因是 flaky。新 CI 仍须对本提交运行。
