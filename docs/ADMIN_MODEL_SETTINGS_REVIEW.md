## 已检查的安全与运行边界

- 控制器在读配置前验证会话，在写配置前验证固定 Origin、会话和 CSRF。登录有全局限速；会话 ID 随机、服务端保存其哈希，Cookie 为 HttpOnly/SameSite=Strict，HTTPS 场景设置 Secure。过期、退出及 API 重启均使会话失效。
- 接口不返回密钥、前缀、尾号或指纹；错误使用固定词表，审计只记录动作、版本与时间。页面不把管理员凭据、CSRF 或供应商密钥写入浏览器持久存储。
- AES-GCM 文件具备认证格式、随机 nonce、大小上限、目录/文件权限和属主检查、符号链接及硬链接拒绝。写入采用临时文件、fsync、原子替换、revision CAS 和独占锁。失败不自动回退环境配置。
- active/saved 分开持久化，运行时持有独立 active 副本。启动时存在 running 标题任务则推迟应用；初审认为“查询失败也不应用新配置”，但当时未覆盖被 `storageReady()` 吞掉的元数据查询异常，这一结论在初审时并不完备，见下方补充复审。保存不热切换 Provider，不自动重启服务。
- 管理员存储关闭登录入口后仍可作为配置来源。显式清除密钥不会回退到环境中的旧密钥。管理配置只影响标题创作，不改变旧网页千问助手、CLI 或媒体 Provider。
- 生产环境强制关闭、标题创作功能开关、原操作者令牌、供应商端点白名单、模型白名单及单任务调用上限仍保留。管理 API 不接受这些门控的覆盖字段，不提供付费连通性测试。
- `scripts/admin-models-init.mjs` 只在明确运行时创建仓库外的新私有目录和凭据文件，不覆盖已有目录，不打印凭据，不配置服务或调用模型。
- 浏览器验收入口有显式开关，监听 loopback，使用真实管理 HTTP/认证/加密临时文件和假凭据，无业务数据库，禁止出站 fetch；它不是正式启动入口。

## GitHub 后续审查修复的独立复审

本轮基线为 `1d3770d2329512f5fe6eb30b86dc7a15171a2384`，复审对象是该基线上四个尚未提交文件的差异：`studio.runtime.ts`、`admin-runtime.spec.ts`、`admin-models.tsx`、`admin-models.spec.tsx`。前文初审历史保留；以下是对后续发现和修复的新增判断。

结论：两项发现均已在当前源码中解决，未发现新的 P0/P1 或阻断项。

1. **P1：元数据读取异常被当作没有运行中任务。** 旧实现调用会吞掉查询异常的 `storageReady()`，把 `false` 直接映射为可以激活。修复在 `studio.runtime.ts:104–113` 使用独立 `to_regclass` 查询：只有查询成功且明确缺少 run 表才认定没有任务；表存在时查询本工作区 running 任务；查询异常或无法解释的返回值不激活。异常经 vault 的固定错误映射向上传递，启动过程关闭连接池。`admin-runtime.spec.ts:216–247` 回归分别覆盖元数据 57014、失败后新实例仍保持旧 active 配置及调用上限、明确缺表的允许路径。异常测试恢复了真实 `storageReady()` 实现，数据库边界同时支持旧、新两种查询，未继续用 `storageReady=true` 桩掩盖缺陷。
2. **P2：最近配置活动显示最旧记录。** `admin-models.tsx` 改为 `slice(-8).reverse()`，取得最新八条并倒序显示，且不会原地反转服务端数组。组件回归给九条记录，检查显示 v9 至 v2、排除 v1，并切换供应商触发重渲染验证顺序保持。
