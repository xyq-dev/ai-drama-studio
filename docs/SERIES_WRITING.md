# 系列编剧（1–60 集，2026-10-22）

同一部作品最多 60 集：先做一次全剧规划，再每 3 集一批写完整剧本并逐批全文审阅，批与批之间用连续性台账衔接，最后做一次全剧结构与连续性总检；支持人工修改、人工复核、写入正式分集和当前编剧交付包。本功能只交付文本：不生成图片、语音或视频，60 集媒体生产没有开放。

## 1. 与原短剧流程的关系

- 原标题创作和 AI 自动创作的 1–6 集契约、常量（`TITLE_WRITING_MAX_EPISODES = 6`）、默认值、提示与检查版本、历史任务全部不变。系列编剧是独立模式：独立的契约（`packages/contracts/src/series-writing.ts`）、独立的表（`series_writing_*`）、独立的提示与检查版本。
- 作品新增 `project.writing_mode`（`short` | `series`）。已有作品全部是 `short`，数据库仍把它们限制在 1–6 集（替换后的 CHECK 加触发器，见第 7 节）；只有 `series` 作品可以有 7–60 集。
- 标题创作与 AI 自动创作遇到系列作品直接拒绝（`TITLE_WRITING_SERIES_PROJECT` / `AUTO_CREATION_SERIES_PROJECT`），不发送。
- 媒体生产遇到系列作品一律拒绝（`SERIES_MEDIA_NOT_ENABLED`），与集数和审核链无关：场景/镜头批次与 `assertProductionEpisodes` 之外，公共媒体准入 `assertUsableShotWithClient` 也检查作品模式，所以单镜图片、视频、语音、字幕、音乐的生成、复用该准入的重试和资产提交都在创建任务、尝试、资产或调用之前被拒绝。短剧作品的相同路径不变。角色参考图走独立的准入 `CharacterReferenceStore.prepareGenerationInTransaction`，同样检查作品模式：参考图任务创建和完成提交（`completeGeneration` 复用该准入，重新入队的重试在完成时同样被拒）都在写入任务、尝试、资产或费用之前拒绝系列作品；参考图可选结构未安装时仍先报原来的不可用。作品模式统一由 `projectEpisodePlanIn` 读取，没有系列迁移（无 `writing_mode` 列）的数据库里所有作品都按短剧处理。
- 研究与选题阶段沿用 AI 自动创作的阶段本身（`ads.auto-creation.prompt.v11` / `checks.v14` / `research.v4` / `selection-rules.v1`），含义未变，系列在冻结输入里记录借用的版本，不另立版本。2026-10-25 共享研究提示升为 prompt.v8（每条假设只含 `id`、`statement`、`howToVerify`，见 `docs/AI_AUTO_CREATION.md` 3.7）：新系列冻结 v8；此前创建的系列保留冻结的 v7，之后发送的研究按当前提示执行并在 `executedWith` 记录 v8；系列自身的 prompt / checks 版本不变。2026-10-25 共享检查升为 checks.v8（只在 howToVerify 里把「计划制作三集样稿进行试读」这类样本集数与全剧总集数分开，样本须在 1 到冻结集数之间，见 `docs/AI_AUTO_CREATION.md` 3.8）：新系列冻结 checks.v8；此前创建的系列保留冻结的 checks.v7，之后发送的研究在 `executedWith` 记录 v8。同日共享检查再升为 checks.v9（样本动作必须直接带着当前样本数量，见 `docs/AI_AUTO_CREATION.md` 3.9）：新系列冻结 checks.v9，旧系列保留冻结的 v7 或 v8，之后发送的研究在 `executedWith` 记录 v9。2026-10-26 共享研究升为 prompt.v9 / checks.v10（内容结构的方法引用改为从规划任务自己保存的 sources 快照切出的目录里选编号，服务端填回原文，落库仍为 research.v4，见 `docs/AI_AUTO_CREATION.md` 3.11）：新系列冻结 v9 / v10，旧系列保留冻结版本，之后发送的研究在 `executedWith` 记录 v9 / v10 及目录版本与哈希。2026-10-26 共享研究再升为 prompt.v10 / checks.v11（验证计划可以只试读本系列的一部分，抽样集数或第几集必须在系列冻结集数之内；作用范围无法确认的集数保留为未核实提示，见 `docs/AI_AUTO_CREATION.md` 3.12）：新系列冻结 v10 / v11，旧系列保留冻结版本，之后发送的研究在 `executedWith` 记录 v10 / v11。2026-10-27 共享检查升为 checks.v12（创作设计里的局部集数范围和第 N 集按系列冻结集数核对，作用范围无法确认的保留为未核实提示，见 `docs/AI_AUTO_CREATION.md` 3.13）：新系列冻结 checks.v12，旧系列保留冻结版本，之后发送的研究在 `executedWith` 记录 v12；prompt.v10 和系列自身 prompt.v1 / checks.v1 不变。同日共享检查再升为 checks.v13（验证计划里的「第一阶段」「第一项测试」「第一轮」等流程序数不再当作排名，真实排名和指标名次照旧拒收，见 `docs/AI_AUTO_CREATION.md` 3.14）：新系列冻结 checks.v13，旧系列保留冻结版本，之后发送的研究在 `executedWith` 记录 v13。2026-10-28 共享研究升为 prompt.v11 / checks.v14（application 提示区分叙事时间安排与观众效果；未标记的观看时长不再遮住同一字段里其后的统计；观众自己作出的选择里的「是否」不算待验证，见 `docs/AI_AUTO_CREATION.md` 3.15）：新系列冻结 v11 / v14，旧系列保留冻结版本，之后发送的研究在 `executedWith` 记录 v11 / v14；系列自身 prompt.v1 / checks.v1 不变。没有近期市场资料时沿用 limited 契约（AI 创作策划、受众待验证、市场证据不可用）。

### 2.1 分幕伏笔依赖提示（2026-10-28）

系列提示 v2 只加强 `arc` 阶段的依赖说明和示例。`dependsOn` 指本伏笔兑现前必须已经兑现的前置伏笔，不是编号顺序、数组顺序或埋设先后；没有实际前置依赖时用 `[]`。输出前逐边核对 `dependency.payoffEpisode < current.payoffEpisode`，同时核对引用存在、不是自身，以及每条伏笔的埋设集严格早于兑现集。示例按冻结集数适配：1 集没有可跨集兑现的伏笔，2 集可以有独立伏笔但无法排出严格提前兑现的依赖链，3 集及以上才展示合法的两条依赖示例；示例不要求作品照搬内容或固定伏笔数量。

校验仍为 `checks.v1`，没有放宽同集兑现、倒置依赖、自引用或循环的拒收，不自动删依赖、调整集号或重发。`plan_structure@foreshadowing[4].dependsOn` 在当前校验器里表示第五个条目的某项依赖同集或更晚兑现；它不表示该条目一定叫 FS5，也不包含具体集号。该分支的内部详情为 `dependency_not_paid_earlier`，仍按原有错误码格式持久化，拒收正文不保存。

新系列和新子任务冻结 `prompt.v2`；历史系列与子任务的 v1 输入、哈希、调用、产物和费用不回写。执行系列独有阶段时按**子任务冻结的提示版本**构造请求：已有 v1 子任务仍发送原 v1 提示，后来创建的 v2 子任务使用 v2；旧系列可以拥有新版本子任务，系列创建时版本与各子任务版本分别保留。研究与选题继续借用共享 `prompt.v11` / `checks.v14`，不受这次系列提示升级影响。HTTP 字段、数据库结构、预算和幂等规则不变，无 Migration。

离线合成样本和模型替身验证的是提示内容、边界与执行保护，不证明真实模型下一次一定遵守，也不能还原历史被拒输出。线上已完成的 research、directions、setting 保留；本次代码变更不会自动续跑任何任务。

## 3. 阶段与调用公式

| 子任务 | 阶段 | 正常调用 |
| --- | --- | --- |
| 全剧规划 | sources（本地）、research、directions、setting、arc、outline:1…⌈N/6⌉、plan_review | 4 + ⌈N/6⌉ + 1 |
| 第 b 批 | episode:(3b−2)…(3b)（最后一批可少于 3 集）、batch_review:b | 本批集数 + 1 |
| 全剧总检 | final_review | 1 |

正常调用 = **6 + ⌈N/6⌉ + N + ⌈N/3⌉**：60 集全剧规划 15 次；规划加前 3 集正文及该批审阅 19 次（不含总检）；全部正文及检查 96 次。这是每步首次成功、零修改、零重发的次数，不是含重试的最坏预算，也不是付费授权。UI、API 和引擎共用 `seriesScopeCalls` 等纯函数。

- 每个子任务（一次规划、一批、一次总检）就是一次运行，`call_cap` 不超过既有的 60 次；普通任务的 call_cap 没有提高。
- **授权（grant）**：确认卡冻结范围、正常调用、重发次数（0–2，由人选择）、预算 = 正常 + 重发、供应商、模型、输出上限和卡片所基于的规划修订；服务端按公式重算，数字不一致即拒绝（`SERIES_CARD_STALE` / `SERIES_BUDGET_MISMATCH`）。后来的配置变化不会替换已冻结的供应商、模型、范围或预算；新的预算只能是新的授权，历史授权、冻结输入、哈希和调用记录不改写。
- 每次发送在工作区调用锁内**同时**预约子任务额度、授权预算和 24 小时共享日限额，任一不足即停在发送前。已发出但失败、超时或结果未知的调用都计入；本地发送前的校验失败不记为发送。
- **发送前的最后核验**：子任务冻结的规划、故事、台账、前一集和任务接管关系（`seriesJobUpstreamChange`，与续跑同一套规则）在两个持锁步骤里重新读取：预约调用时，以及标记为已提交（发送准入）时。两种 store 都按 子任务 → 授权 → 作品 的顺序加锁（工作台保存故事和剧本先锁作品行，所以二者串行，无反向加锁）。预约前发现变化：不预约、不计数。预约后、准入前发现变化：这次调用以 `upstream_changed_before_send` 结束（记录保留，确定未发送），子任务、授权和共享日限额各归还一次（日限额不计这个错误码）。引擎随即停止子任务等待人工（不重新预约、不重建请求、不重试）；恢复、重复执行或迟到的执行者不会再次归还或提交。
  线性化点是「标记已提交」事务的提交：在它之前提交的工作台修改会阻止发送；在它之后的修改按发送后变化处理——这次调用照常计费、不退还、不自动重发，下一次发送前按原有上游变化规则停止。供应商 HTTP 请求期间不持有数据库事务或行锁，数据库提交与外部请求之间没有原子性。
- **确定未发送的预约归还额度**：执行者在预约之后、标记已提交之前丢失（崩溃、重启），租约过期后的恢复把这次调用记为 `rejected / executor_lost_before_send`（记录保留），阶段回到待发送，并把子任务、授权的已用次数各减 1；共享日限额统计同样不计这类调用（以及取消在发送前关闭的 `canceled_before_send`），三处口径一致。恢复只处理仍为 reserved 的调用，重复执行不会重复归还；旧执行者迟到时既不能再提交也不能结算。已提交（submitted）或结果未知（unknown）的调用一律不归还、不自动重发。
- **日额度准入只看当前这一步**（这一子任务的待发送次数），不要求一天先具备 96 次；子任务之间额度不足会停在两步之间（`daily_quota_low`），之后续跑不重发已完成部分。
- 续跑（同一授权）或交接到下一个子任务前，都要求「已用 + 剩余范围的正常调用」不超过授权预算，所以授权不会开始做不完的工作；不足时停止，不换任务补发、不换供应商、不追加预算。
- 新系列流程默认**不自动修改、不自动重试**：机器发现问题时标为待修改或待复核，并停止后续调度。

## 4. 规划、正文与连续性

- **规划修订**：设定（人物 C1–C12、关系、秘密与知情边界、地点、道具及初始持有人、核心冲突、关键选择、失败代价、唯一结局、主要转折）、分幕（连续覆盖 1–N）、伏笔（FS1–FS16，埋设集 < 兑现集；依赖的伏笔必须严格早于本伏笔兑现，同集兑现或互相依赖都拒收）、1–N 集细纲（目标、阻碍、选择、转折、结果、结束状态、下一集承接、出场人物与地点、按分幕计划埋设/兑现的伏笔）。禁用题材只在创作文本里按字段路径查找（例如 `core.ending`、`scenes[].action` 是正文；`schema`、人物/地点等编号、引用、`intExt`、分集 `ending`、连续性伏笔的 `action` 是协议字段，不参与匹配；同一个词出现在正文里仍拒收），模型输出与人工规划同一规则。程序拒收：集号不连续、引用无效、同一方向的一对人物（from→to）写了两条关系（C1→C2 与 C2→C1 是两对；`duplicate_id`，不做关系语义裁判）、伏笔与分幕计划不一致、结局不在第 N 集（`finale_misplaced`）、超过人物/地点上限、禁用题材。人工修改规划同样检查；每集 `continuity` 里同一对人物也只能出现一次。规划审阅后形成冻结的规划修订（内容哈希），并在作品没有故事时存为故事 DRAFT。
- **正文**：每集是完整剧本（场次、地点、出场人物、动作、对白、声音、关键画面、各场计划秒数），另有独立的一句话概要 `summary`（与这一版正文一起保存）、交接事实和 `continuity`（本集变化的人物位置与已知/未知信息、关系、道具归属、冲突、秘密揭露、伏笔埋设/兑现）。`plannedSeconds` 是写作计划篇幅，没有真人读演不写成实测。第 3、6 等批末集 `ending` 必须是 `continue`，只有第 N 集是 `finale`。
- **连续性台账**：程序从规划的初始状态起，逐集合并 `continuity` 得到当前状态；每批完成时存一份台账修订，绑定规划修订 ID 与哈希、规划绑定的故事修订与哈希、上一批台账哈希和本批各集版本哈希。下一批读取它，不读取无上下文的正文。
- **审阅的依赖**：批次审阅记录它实际读取的全部依赖——规划、故事、本批开始前的台账（第 1 批为规划初始台账，`baseLedger`）和本批各集版本；其中任一与当前不同，审阅即为「待复核」。只确认台账不等于复核：上游台账变化后，后批的旧审阅保持待复核，直到有绑定完整依赖的人工复核。全剧总检同样比较规划、故事、最后的台账和各集版本。
- **矛盾检查**（批次审阅的程序部分，高严重度即不能通过）：道具交接时原持有人或接收人不在场、秘密揭露时无知情者在场或揭露对象不在场、秘密没有在计划集首次揭露（见下）、伏笔未埋先兑现或计划集未埋/未兑现、解决不存在或已解决的冲突、场次/台词/计划秒数超限。模型审阅的问题必须逐字引用被审文本的某一个字段才会被采纳。程序问题（`deterministic`）与模型审阅结论（`verdict`、`issues`）分别保存：模型写「通过」不会抹掉程序发现的高严重度问题，`passed` 仍为否，按既有人工复核流程处理，不自动批准故事或剧本。
- **秘密的计划揭露集**（人物知情，不含观众知情）：`revealEpisode` 是秘密第一次告诉一位原本不知情的人物的那一集；规划里的持有者和 `knownBy` 开始时就知情，告诉他们不算揭露，向已知情者重复陈述也不算完成计划揭露。按规划、阶段输出和台账推导「是否已首次揭露」（台账知情者中出现开始时不知情的人物），不新增字段或迁移，也不只看模型碰巧写出的 `continuity.secrets`：提前首次揭露、计划集没有首次揭露（该条缺失或只向已知情者重复）、延后才首次揭露都是高严重度问题（`secret_schedule` / `secret_missing`），全剧总检对到结束仍未首次揭露的计划秘密报 `secret_unrevealed`。首次揭露之后告诉其他人物属于正常传播，仍受知情者在场、接收人在场的原有检查。`revealEpisode` 为 null 不限集号。所有人物开始时都已知情、计划揭露无法成立时，模型设定与人工规划都以 `plan_structure`（`secret_reveal_impossible`）拒收，已有的这类规划在计划集明确报「规划矛盾」，不自动增加人物或伪造事件。这只检查结构化记录，不能证明正文真的写出了揭露场景，正文仍由全文审阅和人工审核判断。
- **已解决的冲突不再打开**：台账（含同一子任务里前面各集合并后的台账）里已 `resolved` 的冲突，模型输出不能用同一编号写回 `open`：在接受输出、合并台账之前即拒收（`plan_structure@continuity.conflicts[i]`，规则 `conflict_reopened`），不改写台账、不悄悄忽略这条更新；新的矛盾使用新的冲突编号。未解决冲突的延续、open→resolved、已解决冲突之后新增其他编号照常；`openedIn`、`resolvedIn` 与历史台账不改写。人工台账纠错不受此限（人工确认流程不变）。
- **人工台账必须保留全部固定实体**：人物、道具、秘密、伏笔四类编号必须与规划完全一致（不缺、不重复、没有未知编号），关系的有向组合不重复；状态（位置、持有人、知情者、伏笔进度）可以人工改，冲突是台账自己的动态记录，不套用规划集合。程序不自动补造缺失的状态，不一致即拒收（`SERIES_INVALID_EDIT`），不新增台账修订。
- **人工修改**：在作品工作台改剧本形成新的剧本修订；该集当前版本变为人工稿，对应台账进入「待确认」，后续台账因链条变化进入「需重新确认」，后续批次停止调度；用户在系列页面确认台账（含每集新概要，绑定当前版本）后才能继续，不增加模型抽取调用。
- **台账确认绑定编辑器打开时看到的版本**：视图为每批给出 `ledgerBasis`：规划修订 ID 与哈希、规划绑定的故事与作品当前故事、前一批台账修订与哈希（第 1 批为规划初始台账）、正在替换的本批台账修订，以及每集的版本身份和哈希。页面在打开台账编辑器时冻结这份依据，后台轮询不会替换它（依据已变化时编辑器内提示）；保存时随请求提交 `expectedBasis`。服务端先比对一次，再在保存事务内重新读取并逐项比较：先取系列行锁，再取作品（project）行锁——工作台保存故事和剧本都先锁作品行，所以顺序是 系列 → 作品（→ 分集），与写入正式分集相同；工作台保存要么在读取依据前已提交（于是在依据里），要么等台账保存提交之后才进行（随后照常使台账待确认）；人工复核记录同样取这两把锁；任一不同返回 409 `SERIES_LEDGER_STALE`，不新增台账修订、不记录概要或确认、不解除阻断，页面保留编辑内容并提示重新读取核对。不会把请求到达时的新剧本哈希绑定到旧概要上。
- **人工复核绑定页面看到的版本**：页面提交复核时带上它显示的依据（`expectedBasis`，即视图里的 `decisionBasis`）：规划为规划与故事；一批为规划、故事、本批开始前台账、各集版本和本批结束后台账；总检为规划、故事、最后的台账和各集版本。服务端在保存事务内（与其他修改相同的系列行锁）重新读取当前依据，不一致返回 409 `SERIES_DECISION_STALE`，不写记录、不解除阻断，也绝不替换成最新版本；页面保留备注并提示刷新。复核不会批准故事或剧本。
- **人工修改规划与故事**：保存规划修订时，同一事务内按新规划形成一份故事新草稿（`from_plan`，默认）并建立关联；页面同时提交它看到的当前故事，作品故事在此期间被另存则返回 409 `SERIES_STORY_CONFLICT`，什么都不写。新故事是 DRAFT，不继承旧故事的批准；原规划、原故事和审核记录保留。新规划经人工复核、故事经正常人工审核后，写入正式分集以这份故事为来源。
- **工作台故事换稿**：规划修订绑定一份故事修订（及内容哈希），子任务冻结它。工作台另存故事后，新授权、续跑和执行中子任务的下一次发送都会停止（`story_changed` / `upstream_story_changed`），台账也不能确认。同步方式二选一，都形成新的规划修订：「以工作台当前故事为准」（`adopt_current`，绑定那份故事）或「按规划重新形成故事草稿」（`from_plan`）；之后需复核规划、重新确认各批台账并复核各批。写入正式分集只接受规划绑定的故事（已去掉旧的「确认按审核通过的故事写入」开关）。
- **规划阻断在正文开始前也列为待办**：规划存在时 `attention` 一律由 `seriesAttention` 给出（不再要求已写正文）：模型规划审阅有阻断（`plan_review_blocking`）、人工规划尚未复核（`plan_unreviewed`）等在 0 集时同样显示；页面、JSON 与 Markdown 用同一份领域结果，人工复核后随之更新；尚无规划时为「尚未规划」、待办为空，不虚构规划检查结果；尚未开始的批次不列为执行失败。
- **换稿后撤销完成状态**：作品当前故事不是规划绑定的故事时，整包不能是「全剧文本完成」或「审定完成」，而是局部完成，并列出待办（`attention`，首项 `story_changed`）；当前全剧总检视为「待复核」，即使之前通过或已人工复核也不再有效（原总检输出、通过结果和调用记录原样保留，页面与交付包标明「旧版本曾通过总检，不代表当前依赖有效」）。失配期间规划、批次、总检都不能记录人工复核（依据为空，请求返回 409），只能先同步规划与故事，再确认台账、复核各批与总检，状态才按实际有效依赖恢复。页面、Markdown 与 JSON 显示一致；状态变化不会自动重发、建授权或追加预算。
- **来源过期**：故事被替换后，按旧故事写入的工作台剧本变为 STALE；系列不再把它当作原模型稿的有效版本（集状态「来源过期」，`episode_source_stale`），该批台账不能确认，需在工作台按当前故事重新保存这些分集。
- **上游变化**：人工修改规划另存新修订，所有基于旧规划修订的台账变为需重新确认，执行中的子任务在下次发送前停止（`upstream_*`）。缺少前集、有效规划或必要台账时不会续写。
- **复用**：子任务停止后由新授权继续同一批时，前面已完成且依赖未变的阶段直接沿用（记录 `reused_from`），不重发；新子任务的 `call_cap` 按实际待发送阶段计数（不含本地 sources、不含沿用的阶段），仍受授权剩余额度和 60 次上限约束。本轮不支持用模型重写已完成的批次或重新生成规划（只能人工修改）。
- **一批算完成**：这一批有一个子任务完成（各集模型阶段和本批全文审阅都已执行）。当前稿件存在不等于完成：某集模型阶段没完成时人工在工作台补写，这一批仍是「下一批」，新授权接续该批未完成的阶段和本批审阅（已完成的阶段不重发，人工稿不覆盖、仍是当前稿；模型稿另列为未采纳），之后按既定流程确认台账、人工复核，再继续下一批。
- **被取代的规划授权**：一次规划子任务之后已有规划修订（另一授权或人工保存），或已有更晚的规划子任务，它就被取代：续跑和下一次发送前都拒绝（`upstream_plan_superseded`，`SERIES_UPSTREAM_CHANGED`），不新增子任务、不发送、不新增规划、不改历史预算或输出。
- **被后来授权接管的批次与总检**：同一批次（或全剧总检）有更晚的子任务（按服务端在系列锁下分配的 `job_seq`，不看客户端时间或 ID）时，较早的子任务和较早授权剩余的这一部分即被取代：续跑、创建下一子任务（交接或续跑时，取这次授权自己最后一个子任务之后是否已有同批次/总检的子任务）、两种 store 持锁预约每次调用、以及保存台账等结果前都拒绝（`upstream_job_superseded`，`SERIES_UPSTREAM_CHANGED`）。被拒的续跑零发送、不新增子任务、调用或续跑记录，不覆盖后来授权的正文、台账、审阅或总检；已提交或结果未知的调用保留原有费用与恢复规则。
- **授权只用自己的规划修订**：授权允许使用的规划依据由领域层 `seriesGrantPlanRevisionId` 统一给出：不含规划生成的授权取确认卡上的 `basePlanRevisionId`；含规划生成的授权取这次授权自己已完成的规划子任务保存的模型规划修订（按 `sourceRunId` 与子任务归属推导，找不到唯一一份即视为没有依据），绝不取恢复时的最新规划或其他授权的规划。按修订身份比较，正文相同的新修订也算换版。当前规划不是这份修订时，停在子任务之间的续跑、自动衔接下一批或总检（两种 store 在持锁事务内读到的状态上判断）、已存在子任务的续跑与每次发送前检查（含 store 持锁预约与提交）都拒绝（`upstream_plan_changed`，`SERIES_UPSTREAM_CHANGED`），即使台账、复核等当前阻断已全部解除，或子任务自己的输入冻结的正是新规划。被拒时零发送、零新增预约、不新增续跑记录或子任务，不改正文、台账、规划、审阅、总检，不回写授权或子任务输入，不自动建新授权、不转移剩余额度；已预约未提交的调用按既有机制关闭为未发送并只归还一次，已提交或结果未知的调用照常计费、不自动重发。继续创作需基于新规划由用户重新确认新的授权。

- **写入正式分集**：候选是这一批已完成子任务中尚未处理的各集模型阶段（不是当前稿）：某集已有工作台剧本（人工先写）时保留人工稿并记为冲突，不会因为当前稿是人工稿而从检查中消失；页面按「已写入 + 冲突」判断是否处理完，处理完不再显示写入按钮，重复点击不重复写入。只在依赖有效时写入：台账有效或已确认（不是待确认或需重新确认）、全文审阅不是缺失或待复核、没有来源过期的分集、作品当前故事是规划绑定的故事；模型正文按该子任务冻结的规划修订格式化，绝不套用新规划的设定。服务层先判断一次，store 在持锁事务内（系列 → 作品 → 分集）按读到的状态重新计算候选并核验；过期依赖下零写入。
- **全剧总检绑定实际概要**：总检依据的每集一项是「该集概要文本 + 它所属的版本身份」的哈希（`seriesSummaryBasisHash`）；提示上下文、总检记录的 reviewed、失效判断和人工复核用同一套依据。只改人工台账里的概要也会使旧总检变为待复核（原输出、调用、费用原样保留），不会自动发送新的总检。人工复核只能复核或覆盖已经完成的模型总检：从未有完成的总检输出时，视图不提供总检的复核依据，服务端拒绝保存（409，零写入、零调用），状态计算也不会因人工记录而变为完成；首次总检仍按同一依据正常执行。

## 5. 上下文预算（字符）

提示上限 40,000、审阅正文预算 28,000、单次输出 4096 tokens 均未改变。各文本有固定上限，超出整份拒收（`too_large`），不截断、不删用户约束、不跳审阅、不暗中缩批：

| 文本 | 上限 |
| --- | --- |
| 设定 JSON | 6,000 |
| 分幕 JSON（其中伏笔表 3,000） | 4,500 |
| 每集细纲单行 | min(600, ⌊17,500 / N⌋)，N=60 时 291 |
| 台账 JSON | 7,000 |
| 每集 JSON | 3,300 |
| 总检每集概要行 / 每批摘要 | 90 / 120 |

- 规划审阅：设定 + 分幕 + 全部细纲单行 ≤ 28,000（N=60：6,000 + 4,500 + 17,460）。
- 批次审阅（各批全文检查）：设定 + 本批细纲 + 本批开始前台账 + 未兑现伏笔 + 本批 3 集全文 ≤ 27,700。
- 全剧总检（结构与连续性总检）：固定版本的设定与分幕、全剧结束时的台账、各批审阅结果和每集独立概要 ≤ 25,300；**不逐字读取各集正文**。
- `seriesReviewShares(N)` 对 N = 1…60 逐一测试份额非负。

## 9. 交付包与完成状态

当前编剧交付包读取实际当前的规划修订、故事和各集版本（工作台人工稿优先）。有工作台剧本的分集（人工稿或已写入的模型稿）导出其保存的原文，与标注的修订 ID、哈希逐字一致；没写入工作台的模型稿和未采纳的模型稿按其子任务冻结的规划修订格式化，不套用当前新规划。故事部分导出工作台实际当前故事的正文、修订 ID、内容哈希、审核状态、新鲜度及与规划的关系（是否为规划绑定的故事）；已批准故事与当前故事不同时另行列出；当前故事不是规划绑定的故事时明确标注，不与规划混写为定稿（Markdown 中规划里的梗概也标为「规划修订中的梗概」）。此外含全剧故事与人物关系、全部细纲、已完成剧本、各批台账与审阅、修订 ID / 内容哈希 / 依赖、新鲜度、缺项和制作注意事项；已批准稿与当前稿不同时分别列出，未采纳的模型稿标明来源。原 AI 自动创作的成品包仍是历史快照，未改动。Markdown 里的故事、剧本（当前稿、批准稿、未采纳的模型稿）和台账 JSON 都放进安全代码围栏（`seriesMarkdownFence`）：围栏的反引号比正文中最长的一段反引号多一个（至少 3 个），正文原样保留（不删改反引号），正文里的标题、链接、列表始终属于该代码块，不会成为交付包的顶层结构；概要、规划字段等行内文本的换行（LF、CRLF 或单独的 CR）合并为空格，不会另起标题或围栏。JSON 导出与实际保存的原文不变。

完成状态：局部完成（如「已完成 3/60 集，其余待写或待复核」）→ 全剧文本完成（全部集数、规划、各批台账与审阅、全剧总检均有效）→ 审定完成（另需当前故事与每集当前剧本都已人工批准）。人工审核、真人读演、实拍计时、媒体生产分别记录；后两项本功能不产生。

## 10. 已知限制

- 台账确认与规划修改在页面上是 JSON 编辑框，不是逐字段表单。规划编辑框打开时冻结它对应的规划修订和故事修订：后台读取不替换（依据变化时提示），保存按打开时的修订提交，别人已另存则服务端拒绝、编辑内容保留；保存成功后关闭，再次打开从刚保存的修订开始。
- 来源过期的分集需要在工作台逐集重新保存；系列页不提供批量重新写入。
- 不支持用模型重写已完成的批次或重新生成规划，也没有定向修改轮次（新流程默认零自动修改）。
- 离线验收全部使用模型替身：证明的是流程、预算、依赖与保护，不证明真实模型能按预算写出合格的 60 集。真实输出能否稳定落在每集 3,300 字符、细纲单行 291 字符以内，需要受限真实验收确认。
- 系列作品的高级编辑页（`/projects/:id`）不在本轮调整范围；其中的媒体操作仍由服务端以 `SERIES_MEDIA_NOT_ENABLED` 拒绝。
- 历史秘密计划集与冲突编号修复发生时，系列提示与检查均保留 v1；当前分幕依赖提示另升为 `prompt.v2`，检查仍为 `ads.series-writing.checks.v1`。
